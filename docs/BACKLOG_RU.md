## A. Аудио: качество звука (мини-рации + T320)

## B. Датчики: архитектура и расширение

### B4. Продумать и написать план архитектуры управления датчиками
Сделать удобно и наглядно. Требования (от Eugene):
- **Отдельная вкладка у СУПЕРАДМИНА** для датчиков.
- **Выпадающая панель** управления.
- **Распределение сигналов** по диспетчерам, группам и абонентам (кто что видит,
  кому какие алармы/push).
- **Настройка порогов** из UI (фундамент уже есть — per-sensor JSON thresholds).
- В целом — продумать весь UX управления датчиками.
- База уже заложена: см. governance-модель и roadmap в `docs/SENSORS_RU.md`
  (SUPERADMIN регистрирует устройство, ADMIN настраивает/раздаёт, DISPATCHER
  мониторит). Этот пункт = довести до полноценного UI/UX.

### B5. Датчик уровня воды (затопление / наводнение / протечка)
Подключить датчик протечки/уровня воды. ВАЖНО: **уровень воды — это ЦИФРЫ**
(значение уровня см/%), а не булево «да/нет» как движение/дверь. То есть нужен
ЧИСЛОВОЙ диапазон-порог (как температура), а не событие. Плюс отдельно «факт
протечки» может быть булевым. Вписать в универсальные метрики (B8).

### B6. Датчики по LoRa + единая система датчиков
- Подключение датчиков по протоколу **LoRa** (LoRaWAN / прямой LoRa).
- **Объединить ВСЕ датчики в единую наглядную систему** с алармами. Сейчас у
  каждого датчика свой сайт/своя панель (Frigo → frigo.privox.tech, HomeClimate
  → temperature.privox.tech). Свести в один дашборд PrivoxPTT с тревогами,
  **сохранив возможность индивидуального наблюдения** за каждым датчиком отдельно.
- Связано с уже сделанным firmware-free поллингом (см. `docs/SENSORS_RU.md`):
  тот же подход (адаптер/стандартный POST) расширяется на LoRa-шлюз и новые типы.

### B8. Универсальные метрики + унифицированный протокол (когда железо готово / чуть позже)
Сейчас метрики только temperature/humidity, пороги захардкожены под них. Обобщить:
- **Адаптеры** → выдают именованные метрики `{ temperature, humidity, waterLevel, leak, motion, doorOpen, co2... }`.
- **Типы порогов:** ЧИСЛОВОЙ диапазон (темп, влажность, **уровень воды — это цифры!**, CO₂) vs БУЛЕВО/событие (движение, дверь открыта, факт протечки — «тревога когда true»).
- **Проверка порогов** обобщается на любую метрику (сейчас только temp/humidity).
- **Динамический UI порогов** под метрики конкретного датчика.
- **Стандартный `POST /api/telemetry`** = унифицированный протокол телеметрии
  `{ sensorKey, metrics: {...}, ts }` → новые устройства шлют без кода (plug-and-play).
- Составить единый протокол подключения датчиков.

### B9. Переход WiFi → LoRaWAN (датчики)
Скорее всего перейдём с WiFi на **LoRaWAN** — ради дальности и экономии энергии.
Влияет на onboarding: LoRaWAN-шлюз → стандартный telemetry-эндпоинт (B8). Спланировать
вместе с унифицированным протоколом.

### Конвенция
UI и **названия датчиков — на английском** (как остальное приложение).

## C. Радио: индикация / UX

### C7. Все статусы на OLED вместо отдельного индикатора
Дисплей сейчас почти дублирует световой индикатор (Ready/TX/RX/Connecting).
Вывести ВСЕ статусы (зеркало LED) на **верхнюю строку OLED**, тогда отдельный
индикатор не нужен:
- Верхняя строка = короткий токен: `NO NET` / `CONNECTING` / `AUTH ERR` /
  `READY` / `TX` / `RX` (1:1 с цветами LED, чтобы не противоречили).
- Центр/низ = группа + канал (как сейчас); при проблеме — человекочитаемая
  **подсказка с действием** («Нет сети — удерживай кнопку 3с для настройки»,
  «Ошибка входа — проверь логин»).
- **Встроенный WS2812 (GPIO48) оставить только для отладки** / взгляда издалека
  (например, во время передачи, когда на дисплей не смотришь). Внешний индикатор
  не нужен → экономия пина (важно на SuperMini) и пайки.
- Часть уже есть: верхняя строка OLED уже показывает SETUP/CONNECTING/READY/RX/TX
  — нужно дополнить ошибками и инструкциями. Задача по прошивке (udp_radio).

### C-SENSOR-ALARM. Тревога датчика на рацию (НОВОЕ, отложено 2026-06-13)
Сейчас рация тревоги датчиков **не получает в принципе**: прошивка `udp_radio`
общается с сервером только по сырому UDP для аудио (нет Socket.IO, ни одного
упоминания sensor/alert). Тревоги идут только в веб-консоль (Socket.IO) и на
смартфоны (FCM). Чтобы рация сигналила тревогу (бип/LED/строка на OLED) — нужна
новая фича: серверный UDP-пакет тревоги к рациям орга/группы + обработчик в
прошивке (тип пакета «alarm», текст датчика, severity → паттерн бипа/цвет LED,
строка на OLED). Отдельная ветка: сервер (новый UDP-emit к подключённым рациям)
+ прошивка udp_radio. Связано с C7 (статусы на OLED).

### D1. Карточка приглашения не копируется в буфер (отложено 2026-08-18)

| Повторное открытие использованной ссылки | корректно: «This invitation has already been used», подсказка логина, кнопка SIGN IN |

**Главное, чего в описании не хватало:** приглашения одноразовые
(`Invite.maxUses` по умолчанию 1, мастер по умолчанию ставит «Single use»).
Но **простое открытие ссылки её не тратит** — расходует только нажатие
JOIN. Поэтому заявленный на самой странице сценарий («Install it, then open
this same link again — the invitation stays valid») работает: проверено, после
открытия и скачивания APK приглашение осталось `VALID`.

**Обратная сторона:** если человек нажал JOIN в браузере, а потом поставил
приложение и открыл ту же ссылку — увидит «уже использовано». Тупика нет,
страница показывает его логин и кнопку входа, но лишний шаг есть. Многоразовое
приглашение эту развилку убирает: мастер → шаг приглашений → `INVITE REUSE` →
`Reusable until expiry`. Для существующей группы тот же шаг доступен через
кнопку `Add` на карточке — заново создавать группу не нужно.

**Расхождение умолчаний (не стреляет, но лучше свести):** в мастере
`singleUse` по умолчанию `true`, а серверная схема при отсутствии поля
подставляет `false` (`onboarding.ts` → `singleUse: z.boolean().default(false)`).
Сейчас безопасно, потому что UI всегда шлёт значение явно.

**Как это проверялось — пригодится в следующий раз.** Сканировать камерой не
нужно: QR кодирует обычную ссылку, и её открывает
`adb shell am start -a android.intent.action.VIEW -d "<url>"`. Это то же самое,
что нажатие на результат сканирования, но позволяет принудительно направить
ссылку в приложение или в браузер (`-n com.android.chrome/...Main`) и снимать
экран через `exec-out screencap`. Состояние приглашения читается без расхода:
`GET /api/invites/<token>` — **проверять состояние ДО открытия**, иначе легко
потратить попытку впустую.

### D14. iOS на MacBook Air M1 (в работе, 2026-08-20)
macOS обновляется до Tahoe 26.6.2 — Xcode требует 26.2+. Порядок:
Xcode → клон репозитория вне iCloud → Capacitor iOS-проект → сборка и
установка на iPhone по кабелю → Apple Developer Program ($99) → TestFlight.

От Eugene: установка Xcode, вход под Apple ID, режим разработчика на iPhone,
подтверждение доверия. Остальное — моя часть.

**Сделано:** `ios/phone/` — Capacitor-обёртка (Swift Package Manager вместо
CocoaPods, так в Capacitor 8), собрана и поставлена на живой iPhone через
Xcode (Developer Mode + бесплатный Apple ID, без платного аккаунта). Добавлены
`NSMicrophoneUsageDescription`/`NSLocationWhenInUseUsageDescription` в
Info.plist — без них WebView тихо блокировал доступ к микрофону, PTT на
передачу не работал вообще. После фикса приём и передача на переднем плане
работают.

**Оговорка подтверждена практически:** при сворачивании приложения — тишина,
статус на дисплее рации падает в offline, звонки не приходят. WKWebView
замораживает JS в фоне независимо от `UIBackgroundModes`. Это системное
ограничение, не баг конфигурации.

**Архитектура фонового режима — решено делать в два этапа:**
1. **Фаза 1 (следующая):** CallKit "звонок-будильник" — push поднимает
   нативный полноэкранный экран входящего звонка даже из killed-состояния,
   пользователь жмёт "Ответить" → открывается WebView → обычный PTT. Не даёт
   постоянного фона, только точку входа. ~неделя работы (сервер: расширить
   `sendIncomingUserCallPush`; iOS: `PKPushRegistry` + `CXProvider`).
2. **Фаза 2 (позже, крупный этап):** настоящий фоновый приём/передача через
   нативный Apple PushToTalk Framework (`PTChannelManager`, обязателен с
   iOS 26 для рация-приложений, так работает Zello) — требует нативного
   аудио-моста в обход WebView, вероятно на базе стороннего Swift-враппера
   `VLprojects/mediasoup-client-swift` (community, не официальный от
   mediasoup team — сверить версию с сервером 3.13.24 до старта). Оценка:
   3-5 недель на приём + 1-2 недели на передачу из фона + обкатка.

Оба этапа требуют платный Apple Developer Program ($99/год, Individual —
юрлица PRIVOX пока нет) — push недоступен на бесплатном сертификате ни в
каком виде. Тестирование до публикации в App Store — через TestFlight
(Public Link, до 10 000 тестировщиков, без публичной витрины).

**Отдельно уточнили и важно не путать:** сканирование QR-приглашения
(`/join/<токен>`) сейчас всегда открывает Safari, не нативное приложение —
нужны Universal Links (iOS-аналог нерешённого Android-пункта D6). До этого
QR-онбординг веб/PWA-путём (уже проверен, см. D3) остаётся лучше нативного
приложения для входа новых людей; нативное приложение имеет смысл только
ради фонового звука.

**Пауза 2026-08-20 — оформление Apple Developer Program НЕ начато.** По ходу
разговора выяснили, что кнопка "звонок" в приложении (индивидуальная, у
конкретного абонента) вела только в обычный групповой канал, а не в приватный
разговор — сначала имело смысл починить саму суть звонка, а не тратить $99 на

### D7. Сроки групп и права участников — ✅ СДЕЛАНО и проверено 2026-08-21
Было: `Group.startsAt/endsAt/status` и `GroupMember.canMessage/canShareLocation`
заполнялись, но ни на что не влияли — истёкшая группа продолжала работать,
запрет сообщений ничего не запрещал.

**Принятые решения (Eugene, 2026-08-21):**
- Срок группы действует на **все роли, включая SUPERADMIN**. Просроченная
  группа — это закрытый канал, а не канал с исключениями. Админ чинит её,
  продлевая срок, а не разговаривая в ней.
- **Чтение истории остаётся открытым всегда.** Срок закрывает канал, но не
  стирает сказанное: разбор смены после её окончания должен быть возможен.
- Истечение срока посреди эфира обрабатывается **мягко** — без фонового
  планировщика и выкидывания из комнаты. Блокируется следующее действие.

**Правило, по которому расставлены проверки:** окно глушит только НАЧАЛО нового
трафика; уже начатое доигрывает. Иначе истечение срока в момент передачи
оставило бы висеть PTT-локи и комнаты mediasoup.
- Блокируются: `join-group`, `ptt-start`, `user-call-request`,
  `group-call-request`, `dispatcher-call-request`, отправка сообщений и вложений.
- Не блокируются: `ptt-stop`, `leave-group`, `user-call-response`, `call-hangup`,
  `call-leave`, `dispatcher-call-accept` (завершение уже размещённого вызова).
- `sos` намеренно оставлен открытым: это аварийный сигнал, он уходит org-wide,
  и глушить его из-за календарной даты нельзя.

**Реализация:**
- `server/src/services/groupAccess.ts` — новый общий модуль, чтобы сокет и REST
  судили по одному правилу: `checkGroupWindow()` (границы включительные,
  `null` = бессрочно), `openGroupFilter()` (тот же критерий как WHERE для БД),
  `assertPeriodOrder()`. Покрыт `groupAccess.test.ts` — 15 тестов, БД не нужна.
- `server/src/socket/ptt.ts` — `canAccessGroup` (членство и организация)
  разделён с новым `canUseGroup` (членство + открытое окно). Причина отказа
  доходит до клиента в `channel-locked.reason`/`message`, а не подменяется
  общим `no_speak_permission`, как было.
- `location-update` наконец проверяет `canShareLocation`. Право кешируется на
  30 с: точки идут с частотой GPS, поход в БД на каждую положил бы базу. Пока
  человек на канале — судим по правам в этой группе; вне группы разрешаем,
  только если хотя бы одно членство в **открытой** группе это позволяет,
  иначе запрет обходился бы простым выходом из группы.
- `server/src/routes/messages.ts` — у `assertGroupAccess`/`assertDirectAccess`
  появился `intent: 'read' | 'write'`. Личка тоже закрыта: право на неё
  выводится из общей группы, поэтому на запись общая группа должна быть открыта
  и `canMessage` в ней выставлен — иначе запрет обходился бы личкой.
  Привилегированные роли этим не ограничены (путь эскалации).

**Что пришлось доделать, иначе фича стреляла бы в ногу:**
- **Продлить группу было нечем.** `startsAt/endsAt/status` задавались только
  мастером при создании, `PUT /api/groups/:id` их не принимал. С включённой
  проверкой истёкшая группа стала бы неисправимой. Теперь поля принимаются на
  создание и правку, есть UI в `AdminGroups` (STATUS + STARTS AT / ENDS AT,
  пустые даты = бессрочно).
- **Клиент молча проглатывал отказ.** `socket.on('error')` на вебе не было
  вообще — вход в закрытую группу проваливался без единого следа, человек в
  поле видел просто нерабочую рацию. Добавлен обработчик; закрытые группы
  помечаются в списке на экране рации (`web/src/utils/groupWindow.ts`).
- **`canMessage`/`canShareLocation` нельзя было выставить после создания.**
  `PATCH /api/groups/:id/members/:userId` принимал только `canSpeak`. Теперь
  принимает все три по отдельности, в UI участников — три переключателя.
- **Дыра того же рода: `accessExpiresAt` был мёртв целиком.** Срок доступа
  человека проверялся только при логине и refresh, а access-токен живёт 7 дней
  (`JWT_EXPIRES_IN`) — рация уволенного продолжала работать почти неделю.
  Проверка добавлена в хендшейк (`socket/index.ts`). **На смоуке выяснилось
  худшее:** поле читалось в четырёх местах (логин, refresh, активация
  приглашения, хендшейк) и **не записывалось нигде** — ни `createUserSchema`, ни
  `updateUserSchema` его не принимали, так что срок доступа всегда был null и
  вся возможность была неработоспособна. Теперь оба роута его принимают

  в прошлое, сразу стирает refresh-токены и рвёт живые сокеты — как это уже
  делалось для `isActive: false`. Иначе человек доработал бы до реконнекта.
- Заодно: `PUT /api/groups/:id` передавал распарсенное тело в `prisma.update`
  как есть, вместе с `organizationId` — админ мог перенести группу в чужую
  организацию. Поле теперь отбрасывается.

### D15. Дуплексная связь для пары абонентов — ✅ СДЕЛАНО и проверено 2026-08-20
Раньше "звонок" (`user-call-request`) был только уведомлением (push + тон);
ответивший попадал в обычную группу с тем же полудуплексным PTT-локом,
реального двустороннего канала не было.

**Решение подтвердилось верным:** полный дуплекс — только для звонка 1:1,
групповой "будильник" (`group-call-request`) сознательно остался симплексом
(PTT-дисциплина, много голосов разом — каша).

**Реализация** (см. коммит с этой записью):
- `server/src/services/calls.ts` — `TrackedCall` хранит позывной звонящего;
  `completeCall` при `status: 'answered'` и `kind: 'user'` не ставит запись на
  быстрое удаление, а шлёт `call-connected` обеим сторонам с `callId`;
  новые `endCall()` (шлёт `call-ended`, чистит запись) и `isCallParticipant()`
  (для проверки перед входом в комнату). Аварийная самоочистка через
  `MAX_CALL_DURATION_MS` (4 часа) на случай пропущенного hangup.
- `server/src/socket/ptt.ts` — новые эвенты `call-hangup`, `call-join`,
  `call-leave`. `call-join` не идёт через `canAccessGroup` (это не настоящая
  группа в БД) — отдельная проверка `isCallParticipant`. Payload специально
  `{ groupId }`, а не `{ callId }` — так `useWebRTC()` на клиенте шлёт join
  без доработок, просто не зная, что это звонок, а не группа.
- `server/src/mediasoup/router.ts` — новая `closeGroupPeers()`: закрывает всех
  пиров и роутер комнаты целиком по `call-hangup` (эфемерная комната звонка не
  переиспользуется, ждать socket disconnect каждого участника как для обычной
  группы — не нужно и течёт ресурсами).
- `web/src/hooks/useWebRTC.ts` — второй параметр `joinEvent` (`'join-group'`
  по умолчанию либо `'call-join'`); вся остальная логика (produce/consume,
  восстановление после реконнекта, T320 mic gain) переиспользуется без
  изменений — звонок технически неотличим от группы для этого хука.
- `web/src/store/useStore.ts` — `activeCall` (не персистится через
  `partialize`, эфемерное состояние).
- `web/src/hooks/useSocket.ts` — слушатели `call-connected`/`call-ended`,
  helper `hangupCall()`.
- `web/src/components/ui/AlertPanel.tsx` — при ответе на звонок `kind: 'user'`
  больше не редиректит в группу (это было для `kind: 'group'`); ждёт
  `call-connected`.
- Новый `web/src/components/ui/ActiveCallScreen.tsx` — монтируется глобально в
  `App.tsx` вне роутера, сам вызывает `startTransmitting()` сразу при входе
  (без кнопки "держать"), таймер разговора, кнопка HANG UP.

**Технически подтвердилось на практике:** `ms:produce`/`ms:consume` в
`router.ts` не были завязаны на PTT-лок вообще — лок это отдельный
необязательный слой (`ptt-start`/`ptt-stop`), которым звонок просто не
пользуется. Переделка оказалась заметно меньше, чем first оценка (не
"обходить" лок, а просто не использовать этот путь).

**Живой тест 2026-08-20:** два реальных аккаунта, один на компьютере
(`localhost:5173`), другой на iPhone через Safari по локальной сети
(`https://192.168.1.186:5173`, PWA/веб — без нативного приложения). После
починки `MEDIASOUP_ANNOUNCED_IP` (см. ниже) звук пошёл в обе стороны и в
дуплекс-звонке, и в обычном групповом симплексе.

**Важная находка по ходу — `MEDIASOUP_ANNOUNCED_IP=127.0.0.1` ломает ЛЮБОЙ
звук**, как только тестируешь не с одной машины: сигнализация (Socket.IO,
статусы звонка) идёт по HTTP(S) и работает, а сам RTP/UDP-медиапоток пытается
идти на loopback-адрес другого устройства — то есть в никуда. Звонок
"соединяется" визуально, но тишина — на любом типе связи одинаково, это не
баг звонка, это baseline для локальной сети. Чинится выставлением реального
LAN IP компьютера в `.env`.

**Требует того же ограничения, что и любой звонок на iOS:** работает только
пока приложение открыто на экране, до фазы 2 из D14 (нативный фоновый
аудио-мост).

Осталось на потом, не блокирует: рации (T320/мини-рации) сознательно не
участвуют в индивидуальных звонках (отдельный UDP-протокол прошивки,
не Socket.IO/MediaSoup) — решено первой версией не заниматься.

### D18. Беззвучный входящий вызов на Android — ✅ РАЗОБРАНО 2026-08-21 (оказалось не багом)
Жалоба: на Redmi 9A (MIUI 12, Android 10) индивидуальный вызов в спящем режиме
приходил молча — экран входящего с «принять/отклонить» появлялся, вибрация
была, звука не было. На более новом телефоне звонит нормально.

**Причина оказалась одна и простая: громкость звонка на аппарате стояла в 0**
(`STREAM_RING streamVolume:0` при `Max:15`, `Muted:false`). Подняли громкость —
звонит штатно. Ошибки в коде нет.

**Ловушка, на которую стоит не попасться второй раз.** В logcat при КАЖДОМ
вызове на MIUI висит:

    W/MediaPlayer: Couldn't open content://0@settings/system/ringtone_cache
        at android.media.Ringtone.setUri(Ringtone.java:332)

Выглядит как причина, ею не является. MIUI отдаёт из `getDefaultUri()`
служебный адрес-кэш (в system-настройках `ringtone_cache = null`, реальный файл
лежит в настройке `ringtone`), но класс `Ringtone` это переживает: следом идёт
`D/Ringtone: Successfully created local player`, и играет запасной источник.
Предупреждение присутствует и в молчавшем звонке, и в нормально зазвонившем —
проверено на обоих логах. **Не диагностировать по нему.**

**Что сделано в коде:** добавлена одна строка в `PrivoxIncomingCallRinger`
(оба приложения) — предупреждение в лог при `STREAM_RING == 0`. Громкость
намеренно не поднимаем: беззвучный режим это выбор человека. Разбирательство
заняло час, с этой строкой заняло бы минуту.

**Что рассматривалось и ОТКЛОНЕНО:** переписать звонарь с `Ringtone` на
`MediaPlayer`. Писалось под неверный диагноз; `Ringtone` доказанно сам
справляется с подменой адреса на MIUI, а в самописной версии этот запасной путь
пришлось бы воспроизводить руками — и проверить его не удалось, MIUI не даёт
ставить сборку по USB (`INSTALL_FAILED_USER_RESTRICTED`, лечится пунктом
«Установка через USB» в меню разработчика). Раздавать всем пользователям
непроверенный самописный код воспроизведения звука ради гипотетической проблемы
— плохой размен.

### D19. Звонок не зацикливается на Android 7–8.1 (найдено 2026-08-21, НЕ чинится)
В `PrivoxIncomingCallRinger` есть ветка по версии:

    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.P) {   // P = Android 9
        next.setLooping(true);
        next.setVolume(1.0f);
    }

`Ringtone.setLooping()` и `setVolume()` появились только в API 28, поэтому на
Android 7.0–8.1 рингтон играет ОДИН раз вместо 45 секунд и на системной
громкости вместо полной. При `minSdkVersion = 24` эти версии официально
поддерживаются.

**Почему не чинится сейчас:** пострадавших нет и проверить негде. Единственное
устройство на Android 7.1 — рация T320, и на ней звонок слышен нормально:
однократного проигрыша на практике хватает. Чинить вслепую, раздавая сборку
всем, смысла нет.

**Если всплывёт:** лечится переходом на `MediaPlayer` (`setLooping` есть с
API 1, `setAudioAttributes` с API 21 — веток по версиям не нужно вообще), но
тогда обязательно нужен запасной перебор источников звука, иначе на MIUI
получится регресс: `getDefaultUri()` там отдаёт неоткрываемый адрес, и
встроенной страховки `Ringtone` у `MediaPlayer` нет. Рабочий адрес берётся
через `RingtoneManager.getActualDefaultRingtoneUri()`. Проверять обязательно на
живом аппарате Android 7–8.1.

Заодно проверено про «универсальный APK для любого телефона»: он уже такой.
В `build.gradle` нет ни `splits`, ни `abiFilters` — собирается один файл на все
архитектуры, `minSdkVersion = 24` покрывает Android 7 и новее. Отдельная
универсальная сборка не нужна. Файлы лежат в `web/public/downloads/` и уезжают
на сайт вместе со сборкой веба.

### D17. Кнопка побудки на T320 слишком мелкая (2026-08-21)
Колокольчик в нижней панели рации попасть пальцем трудно: экран 240×320,
значок 16 точек, рядом SOS — легко промахнуться не туда. Подумать: увеличить
область нажатия, развести кнопки по краям, или повесить побудку на аппаратную
кнопку (у T320 есть чёрная клавиша 231, сейчас она дублирует PTT).

### D16. Маршрутизация звука — ✅ СДЕЛАНО для Android 2026-08-21, iOS остаётся
Хочется: групповой канал звучит громко (динамик), а индивидуальный дуплекс-
звонок (D15) — тихо "к уху", как обычный телефонный разговор.

Нашли причину и объём работы в `android/t320/.../MainActivity.java:45-127`:
браузер/WebView сам переводит устройство в `MODE_IN_COMMUNICATION`, как только
одновременно активны микрофон и воспроизведение — а это **по умолчанию
направляет звук в тихий наушник**, не на динамик. Для T320 это принудительно
перебивают через `AudioManager.setSpeakerphoneOn(true)` каждые 1500мс
(`forceSpeakerphone()`), потому что рации нужен громкий звук всегда.

У обычного Android-приложения (`android/phone/`) такого принудительного
переключения нет вообще — вероятно, **групповой канал на телефоне уже сейчас
тихий**, если это не проверялось отдельно. Индивидуальный звонок, скорее
всего, и так уже "к уху" без доработок — именно так ведёт себя браузер по
умолчанию.

Что нужно, когда возьмёмся: для `phone`-приложения включать
`forceSpeakerphone()` (по образцу T320) только пока активен групповой канал,
и не включать во время индивидуального звонка — то есть веб-код должен
как-то сообщать нативному Android-слою, в каком он режиме (небольшой
Capacitor-плагин/мост, аналогично уже существующему `PrivoxPushPlugin`).
Для iOS аналогичного нативного кода пока нет вообще — понадобится отдельно
писать через `AVAudioSession.overrideOutputAudioPort`, только когда дойдём
до нативной iOS-разработки (см. D14).

**Сделано 2026-08-21:** нативный плагин `PrivoxAudio` в обоих Android-проектах.
Групповой канал — динамик, личный звонок — наушник, плюс ручное переключение
в шапке и на экране звонка. Маршрут переустанавливается по таймеру: браузер
сбрасывает его на каждом включении микрофона.

Ключевая находка: `setSpeakerphoneOn()` **на Android 12+ работает наполовину**
— динамик включает, а наушник не возвращает. Отсюда две ветки: на новых
версиях устройство вывода выбирается явно через `setCommunicationDevice()`.
Без этого на Android 15 всегда оставался динамик, на Android 10 всё работало —
именно так проблема и проявилась.

У T320 собственный цикл держал динамик всегда; теперь он отступает, когда
плагин просит наушник.

**Осталось для iOS:** тот же смысл через `AVAudioSession.overrideOutputAudioPort`
в `ios/phone`. **Платный аккаунт Apple для этого НЕ нужен** — обычный нативный
код, работает и на бесплатной подписи. Кнопка переключения на iPhone сейчас
намеренно не показывается: приложение проверяет, есть ли чем управлять.

Чисто веб-браузер (без нативной Android/iOS-обёртки) может не иметь
надёжного кросс-браузерного способа управлять этим вообще — `setSinkId()`
даёт выбор между перечисляемыми устройствами вывода, но не гарантированно
экспонирует "динамик" отдельно от "наушника" на мобильных браузерах.

### D4. Конфликт зависимостей в web/ (было до вопросника)
`@vitejs/plugin-basic-ssl@2.3.0` требует Vite 6–8, в проекте Vite 5. Любая
установка пакета в `web/` падает без `--legacy-peer-deps`. Плагин нужен только
для локального HTTPS-режима разработки. Чинится либо откатом плагина до 1.x,
либо обновлением Vite.
