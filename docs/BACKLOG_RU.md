## A. Аудио: качество звука (мини-рации + T320)

### A1. Перегруз/нелинейные искажения на обеих мини-рациях
Звук «как будто перегружен», нелинейные искажения — на **обеих** мини-рациях
(DevKitC и SuperMini). Разобраться: уровень/гейн в аудиотракте, клиппинг на
INMP441→обработка→MAX98357, громкость, GAIN-пин усилителя, питание (3V3 vs 5V).
Возможные места: масштабирование/сдвиг сэмплов в прошивке, насыщение, DC-offset.

### A2. Проверить качество сигнала с микрофона мини-рации (обеих)
Отдельно прогнать/проанализировать сырой сигнал INMP441 на обеих платах —
шум, уровень, искажения ещё до усилителя. (mic_test даёт RMS/min/max — можно
расширить аналитикой.)

### A3. Тихий звук на передачу от T320 — ✅ СДЕЛАНО, подтверждено 2026-08-24
Было: при передаче с Inrico T320 принимающая сторона слышала тихо.

Причина оказалась на стороне рации: её микрофон в `MODE_IN_COMMUNICATION` даёт
заметно более слабый сигнал, чем у телефонов. Лечится не на сервере и не в
кодеке, а усилением исходящего сигнала на клиенте.

**Решение** (коммит `093b907`, `web/src/hooks/useWebRTC.ts`): исходящий поток
пропускается через `GainNode` WebAudio с `RADIO_MIC_GAIN = 8.0`. Усиление
включается **только в режиме рации** — телефоны и веб не затрагиваются, иначе
получили бы перегруз там, где его не было.

Eugene подтвердил 24.08.2026: «мы вроде починили уже передачу с рации, сейчас
всё хорошо».

Значение подобрано на устройстве. Если когда-нибудь появится перегруз на
громких звуках — крутить надо именно `RADIO_MIC_GAIN`, а не общую громкость.

## B. Датчики: архитектура и расширение

### B4. Продумать и написать план архитектуры управления датчиками
Сделать удобно и наглядно. Требования (от Eugene):
- **Отдельная вкладка у СУПЕРАДМИНА** для датчиков.
- **Выпадающая панель** управления.
- **Распределение сигналов** по диспетчерам, группам и абонентам (кто что видит,
  кому какие алармы/push).
- **Настройка порогов** из UI (фундамент уже есть — per-sensor JSON thresholds).
- В целом — продумать весь UX управления датчиками.
- База уже заложена: см. governance-модель и roadmap в `docs/SENSORS_RU.md`
  (SUPERADMIN регистрирует устройство, ADMIN настраивает/раздаёт, DISPATCHER
  мониторит). Этот пункт = довести до полноценного UI/UX.

### B5. Датчик уровня воды (затопление / наводнение / протечка)
Подключить датчик протечки/уровня воды. ВАЖНО: **уровень воды — это ЦИФРЫ**
(значение уровня см/%), а не булево «да/нет» как движение/дверь. То есть нужен
ЧИСЛОВОЙ диапазон-порог (как температура), а не событие. Плюс отдельно «факт
протечки» может быть булевым. Вписать в универсальные метрики (B8).

### B6. Датчики по LoRa + единая система датчиков
- Подключение датчиков по протоколу **LoRa** (LoRaWAN / прямой LoRa).
- **Объединить ВСЕ датчики в единую наглядную систему** с алармами. Сейчас у
  каждого датчика свой сайт/своя панель (Frigo → frigo.privox.tech, HomeClimate
  → temperature.privox.tech). Свести в один дашборд PrivoxPTT с тревогами,
  **сохранив возможность индивидуального наблюдения** за каждым датчиком отдельно.
- Связано с уже сделанным firmware-free поллингом (см. `docs/SENSORS_RU.md`):
  тот же подход (адаптер/стандартный POST) расширяется на LoRa-шлюз и новые типы.

### B8. Универсальные метрики + унифицированный протокол (когда железо готово / чуть позже)
Сейчас метрики только temperature/humidity, пороги захардкожены под них. Обобщить:
- **Адаптеры** → выдают именованные метрики `{ temperature, humidity, waterLevel, leak, motion, doorOpen, co2... }`.
- **Типы порогов:** ЧИСЛОВОЙ диапазон (темп, влажность, **уровень воды — это цифры!**, CO₂) vs БУЛЕВО/событие (движение, дверь открыта, факт протечки — «тревога когда true»).
- **Проверка порогов** обобщается на любую метрику (сейчас только temp/humidity).
- **Динамический UI порогов** под метрики конкретного датчика.
- **Стандартный `POST /api/telemetry`** = унифицированный протокол телеметрии
  `{ sensorKey, metrics: {...}, ts }` → новые устройства шлют без кода (plug-and-play).
- Составить единый протокол подключения датчиков.

### B9. Переход WiFi → LoRaWAN (датчики)
Скорее всего перейдём с WiFi на **LoRaWAN** — ради дальности и экономии энергии.
Влияет на onboarding: LoRaWAN-шлюз → стандартный telemetry-эндпоинт (B8). Спланировать
вместе с унифицированным протоколом.

### Конвенция
UI и **названия датчиков — на английском** (как остальное приложение).

## C. Радио: индикация / UX

### C7. Все статусы на OLED вместо отдельного индикатора
Дисплей сейчас почти дублирует световой индикатор (Ready/TX/RX/Connecting).
Вывести ВСЕ статусы (зеркало LED) на **верхнюю строку OLED**, тогда отдельный
индикатор не нужен:
- Верхняя строка = короткий токен: `NO NET` / `CONNECTING` / `AUTH ERR` /
  `READY` / `TX` / `RX` (1:1 с цветами LED, чтобы не противоречили).
- Центр/низ = группа + канал (как сейчас); при проблеме — человекочитаемая
  **подсказка с действием** («Нет сети — удерживай кнопку 3с для настройки»,
  «Ошибка входа — проверь логин»).
- **Встроенный WS2812 (GPIO48) оставить только для отладки** / взгляда издалека
  (например, во время передачи, когда на дисплей не смотришь). Внешний индикатор
  не нужен → экономия пина (важно на SuperMini) и пайки.
- Часть уже есть: верхняя строка OLED уже показывает SETUP/CONNECTING/READY/RX/TX
  — нужно дополнить ошибками и инструкциями. Задача по прошивке (udp_radio).

### C-SENSOR-ALARM. Тревога датчика на рацию (НОВОЕ, отложено 2026-06-13)
Сейчас рация тревоги датчиков **не получает в принципе**: прошивка `udp_radio`
общается с сервером только по сырому UDP для аудио (нет Socket.IO, ни одного
упоминания sensor/alert). Тревоги идут только в веб-консоль (Socket.IO) и на
смартфоны (FCM). Чтобы рация сигналила тревогу (бип/LED/строка на OLED) — нужна
новая фича: серверный UDP-пакет тревоги к рациям орга/группы + обработчик в
прошивке (тип пакета «alarm», текст датчика, severity → паттерн бипа/цвет LED,
строка на OLED). Отдельная ветка: сервер (новый UDP-emit к подключённым рациям)
+ прошивка udp_radio. Связано с C7 (статусы на OLED).

## D. Вопросник суперадмина

### D1. Карточка приглашения не копируется в буфер (отложено 2026-08-18)
Кнопка `card` на последнем шаге вопросника должна класть картинку в буфер,
чтобы вставить её в Telegram как фото. Не срабатывает. Уже исключено: запись

открыта на localhost (защищённый контекст). Следующий шаг диагностики —
посмотреть, что пишет кнопка (`copied!` или `saved to file`) и что в консоли
браузера; вероятные причины — браузер без поддержки записи картинки в буфер
либо отказ Telegram Desktop принимать вставку.

**Обходные пути работают, задача не срочная:** ссылка отправляется текстом
(кнопка `message`), QR — отдельным файлом (`png`), либо весь список печатается
одним листом (`PRINT ALL QR`).

| Повторное открытие использованной ссылки | корректно: «This invitation has already been used», подсказка логина, кнопка SIGN IN |

**Главное, чего в описании не хватало:** приглашения одноразовые
(`Invite.maxUses` по умолчанию 1, мастер по умолчанию ставит «Single use»).
Но **простое открытие ссылки её не тратит** — расходует только нажатие
JOIN. Поэтому заявленный на самой странице сценарий («Install it, then open
this same link again — the invitation stays valid») работает: проверено, после
открытия и скачивания APK приглашение осталось `VALID`.

**Обратная сторона:** если человек нажал JOIN в браузере, а потом поставил
приложение и открыл ту же ссылку — увидит «уже использовано». Тупика нет,
страница показывает его логин и кнопку входа, но лишний шаг есть. Многоразовое
приглашение эту развилку убирает: мастер → шаг приглашений → `INVITE REUSE` →
`Reusable until expiry`. Для существующей группы тот же шаг доступен через
кнопку `Add` на карточке — заново создавать группу не нужно.

**Расхождение умолчаний (не стреляет, но лучше свести):** в мастере
`singleUse` по умолчанию `true`, а серверная схема при отсутствии поля
подставляет `false` (`onboarding.ts` → `singleUse: z.boolean().default(false)`).
Сейчас безопасно, потому что UI всегда шлёт значение явно.

**Как это проверялось — пригодится в следующий раз.** Сканировать камерой не
нужно: QR кодирует обычную ссылку, и её открывает
`adb shell am start -a android.intent.action.VIEW -d "<url>"`. Это то же самое,
что нажатие на результат сканирования, но позволяет принудительно направить
ссылку в приложение или в браузер (`-n com.android.chrome/...Main`) и снимать
экран через `exec-out screencap`. Состояние приглашения читается без расхода:
`GET /api/invites/<token>` — **проверять состояние ДО открытия**, иначе легко
потратить попытку впустую.

### D14. iOS на MacBook Air M1 (в работе, 2026-08-20)
macOS обновляется до Tahoe 26.6.2 — Xcode требует 26.2+. Порядок:
Xcode → клон репозитория вне iCloud → Capacitor iOS-проект → сборка и
установка на iPhone по кабелю → Apple Developer Program ($99) → TestFlight.

От Eugene: установка Xcode, вход под Apple ID, режим разработчика на iPhone,
подтверждение доверия. Остальное — моя часть.

**Сделано:** `ios/phone/` — Capacitor-обёртка (Swift Package Manager вместо
CocoaPods, так в Capacitor 8), собрана и поставлена на живой iPhone через
Xcode (Developer Mode + бесплатный Apple ID, без платного аккаунта). Добавлены
`NSMicrophoneUsageDescription`/`NSLocationWhenInUseUsageDescription` в
Info.plist — без них WebView тихо блокировал доступ к микрофону, PTT на
передачу не работал вообще. После фикса приём и передача на переднем плане
работают.

**Оговорка подтверждена практически:** при сворачивании приложения — тишина,
статус на дисплее рации падает в offline, звонки не приходят. WKWebView
замораживает JS в фоне независимо от `UIBackgroundModes`. Это системное
ограничение, не баг конфигурации.

**Архитектура фонового режима — решено делать в два этапа:**
1. **Фаза 1 (следующая):** CallKit "звонок-будильник" — push поднимает
   нативный полноэкранный экран входящего звонка даже из killed-состояния,
   пользователь жмёт "Ответить" → открывается WebView → обычный PTT. Не даёт
   постоянного фона, только точку входа. ~неделя работы (сервер: расширить
   `sendIncomingUserCallPush`; iOS: `PKPushRegistry` + `CXProvider`).
2. **Фаза 2 (позже, крупный этап):** настоящий фоновый приём/передача через
   нативный Apple PushToTalk Framework (`PTChannelManager`, обязателен с
   iOS 26 для рация-приложений, так работает Zello) — требует нативного
   аудио-моста в обход WebView, вероятно на базе стороннего Swift-враппера
   `VLprojects/mediasoup-client-swift` (community, не официальный от
   mediasoup team — сверить версию с сервером 3.13.24 до старта). Оценка:
   3-5 недель на приём + 1-2 недели на передачу из фона + обкатка.

Оба этапа требуют платный Apple Developer Program ($99/год, Individual —
юрлица PRIVOX пока нет) — push недоступен на бесплатном сертификате ни в
каком виде. Тестирование до публикации в App Store — через TestFlight

### D7. Сроки групп и права участников — ✅ СДЕЛАНО и проверено 2026-08-21
Было: `Group.startsAt/endsAt/status` и `GroupMember.canMessage/canShareLocation`
заполнялись, но ни на что не влияли — истёкшая группа продолжала работать,
запрет сообщений ничего не запрещал.

**Принятые решения (Eugene, 2026-08-21):**
- Срок группы действует на **все роли, включая SUPERADMIN**. Просроченная
  группа — это закрытый канал, а не канал с исключениями. Админ чинит её,
  продлевая срок, а не разговаривая в ней.
- **Чтение истории остаётся открытым всегда.** Срок закрывает канал, но не
  стирает сказанное: разбор смены после её окончания должен быть возможен.
- Истечение срока посреди эфира обрабатывается **мягко** — без фонового
  планировщика и выкидывания из комнаты. Блокируется следующее действие.

**Правило, по которому расставлены проверки:** окно глушит только НАЧАЛО нового
трафика; уже начатое доигрывает. Иначе истечение срока в момент передачи
оставило бы висеть PTT-локи и комнаты mediasoup.
- Блокируются: `join-group`, `ptt-start`, `user-call-request`,
  `group-call-request`, `dispatcher-call-request`, отправка сообщений и вложений.
- Не блокируются: `ptt-stop`, `leave-group`, `user-call-response`, `call-hangup`,
  `call-leave`, `dispatcher-call-accept` (завершение уже размещённого вызова).
- `sos` намеренно оставлен открытым: это аварийный сигнал, он уходит org-wide,
  и глушить его из-за календарной даты нельзя.

**Реализация:**
- `server/src/services/groupAccess.ts` — новый общий модуль, чтобы сокет и REST
  судили по одному правилу: `checkGroupWindow()` (границы включительные,
  `null` = бессрочно), `openGroupFilter()` (тот же критерий как WHERE для БД),
  `assertPeriodOrder()`. Покрыт `groupAccess.test.ts` — 15 тестов, БД не нужна.
- `server/src/socket/ptt.ts` — `canAccessGroup` (членство и организация)
  разделён с новым `canUseGroup` (членство + открытое окно). Причина отказа
  доходит до клиента в `channel-locked.reason`/`message`, а не подменяется
  общим `no_speak_permission`, как было.
- `location-update` наконец проверяет `canShareLocation`. Право кешируется на
  30 с: точки идут с частотой GPS, поход в БД на каждую положил бы базу. Пока
  человек на канале — судим по правам в этой группе; вне группы разрешаем,
  только если хотя бы одно членство в **открытой** группе это позволяет,
  иначе запрет обходился бы простым выходом из группы.
- `server/src/routes/messages.ts` — у `assertGroupAccess`/`assertDirectAccess`
  появился `intent: 'read' | 'write'`. Личка тоже закрыта: право на неё
  выводится из общей группы, поэтому на запись общая группа должна быть открыта
  и `canMessage` в ней выставлен — иначе запрет обходился бы личкой.
  Привилегированные роли этим не ограничены (путь эскалации).

**Что пришлось доделать, иначе фича стреляла бы в ногу:**
- **Продлить группу было нечем.** `startsAt/endsAt/status` задавались только
  мастером при создании, `PUT /api/groups/:id` их не принимал. С включённой
  проверкой истёкшая группа стала бы неисправимой. Теперь поля принимаются на
  создание и правку, есть UI в `AdminGroups` (STATUS + STARTS AT / ENDS AT,
  пустые даты = бессрочно).
- **Клиент молча проглатывал отказ.** `socket.on('error')` на вебе не было
  вообще — вход в закрытую группу проваливался без единого следа, человек в
  поле видел просто нерабочую рацию. Добавлен обработчик; закрытые группы
  помечаются в списке на экране рации (`web/src/utils/groupWindow.ts`).
- **`canMessage`/`canShareLocation` нельзя было выставить после создания.**
  `PATCH /api/groups/:id/members/:userId` принимал только `canSpeak`. Теперь
  принимает все три по отдельности, в UI участников — три переключателя.
- **Дыра того же рода: `accessExpiresAt` был мёртв целиком.** Срок доступа
  человека проверялся только при логине и refresh, а access-токен живёт 7 дней
  (`JWT_EXPIRES_IN`) — рация уволенного продолжала работать почти неделю.
  Проверка добавлена в хендшейк (`socket/index.ts`). **На смоуке выяснилось
  худшее:** поле читалось в четырёх местах (логин, refresh, активация
  приглашения, хендшейк) и **не записывалось нигде** — ни `createUserSchema`, ни
  `updateUserSchema` его не принимали, так что срок доступа всегда был null и
  вся возможность была неработоспособна. Теперь оба роута его принимают
  (`null` = бессрочно), менять может только администратор, а срок, выставленный
  в прошлое, сразу стирает refresh-токены и рвёт живые сокеты — как это уже
  делалось для `isActive: false`. Иначе человек доработал бы до реконнекта.
- Заодно: `PUT /api/groups/:id` передавал распарсенное тело в `prisma.update`
  как есть, вместе с `organizationId` — админ мог перенести группу в чужую
  организацию. Поле теперь отбрасывается.

**Проверено 2026-08-21 на локальном стенде** — 50 проверок, все зелёные

### D15. Дуплексная связь для пары абонентов — ✅ СДЕЛАНО и проверено 2026-08-20
Раньше "звонок" (`user-call-request`) был только уведомлением (push + тон);
ответивший попадал в обычную группу с тем же полудуплексным PTT-локом,
реального двустороннего канала не было.

**Решение подтвердилось верным:** полный дуплекс — только для звонка 1:1,
групповой "будильник" (`group-call-request`) сознательно остался симплексом
(PTT-дисциплина, много голосов разом — каша).

**Реализация** (см. коммит с этой записью):
- `server/src/services/calls.ts` — `TrackedCall` хранит позывной звонящего;
  `completeCall` при `status: 'answered'` и `kind: 'user'` не ставит запись на
  быстрое удаление, а шлёт `call-connected` обеим сторонам с `callId`;
  новые `endCall()` (шлёт `call-ended`, чистит запись) и `isCallParticipant()`
  (для проверки перед входом в комнату). Аварийная самоочистка через
  `MAX_CALL_DURATION_MS` (4 часа) на случай пропущенного hangup.
- `server/src/socket/ptt.ts` — новые эвенты `call-hangup`, `call-join`,
  `call-leave`. `call-join` не идёт через `canAccessGroup` (это не настоящая
  группа в БД) — отдельная проверка `isCallParticipant`. Payload специально
  `{ groupId }`, а не `{ callId }` — так `useWebRTC()` на клиенте шлёт join
  без доработок, просто не зная, что это звонок, а не группа.
- `server/src/mediasoup/router.ts` — новая `closeGroupPeers()`: закрывает всех
  пиров и роутер комнаты целиком по `call-hangup` (эфемерная комната звонка не
  переиспользуется, ждать socket disconnect каждого участника как для обычной
  группы — не нужно и течёт ресурсами).
- `web/src/hooks/useWebRTC.ts` — второй параметр `joinEvent` (`'join-group'`
  по умолчанию либо `'call-join'`); вся остальная логика (produce/consume,
  восстановление после реконнекта, T320 mic gain) переиспользуется без
  изменений — звонок технически неотличим от группы для этого хука.
- `web/src/store/useStore.ts` — `activeCall` (не персистится через
  `partialize`, эфемерное состояние).
- `web/src/hooks/useSocket.ts` — слушатели `call-connected`/`call-ended`,
  helper `hangupCall()`.
- `web/src/components/ui/AlertPanel.tsx` — при ответе на звонок `kind: 'user'`
  больше не редиректит в группу (это было для `kind: 'group'`); ждёт
  `call-connected`.
- Новый `web/src/components/ui/ActiveCallScreen.tsx` — монтируется глобально в
  `App.tsx` вне роутера, сам вызывает `startTransmitting()` сразу при входе
  (без кнопки "держать"), таймер разговора, кнопка HANG UP.

**Технически подтвердилось на практике:** `ms:produce`/`ms:consume` в
`router.ts` не были завязаны на PTT-лок вообще — лок это отдельный
необязательный слой (`ptt-start`/`ptt-stop`), которым звонок просто не
пользуется. Переделка оказалась заметно меньше, чем first оценка (не
"обходить" лок, а просто не использовать этот путь).

**Живой тест 2026-08-20:** два реальных аккаунта, один на компьютере
(`localhost:5173`), другой на iPhone через Safari по локальной сети
(`https://192.168.1.186:5173`, PWA/веб — без нативного приложения). После
починки `MEDIASOUP_ANNOUNCED_IP` (см. ниже) звук пошёл в обе стороны и в
дуплекс-звонке, и в обычном групповом симплексе.

**Важная находка по ходу — `MEDIASOUP_ANNOUNCED_IP=127.0.0.1` ломает ЛЮБОЙ
звук**, как только тестируешь не с одной машины: сигнализация (Socket.IO,
статусы звонка) идёт по HTTP(S) и работает, а сам RTP/UDP-медиапоток пытается
идти на loopback-адрес другого устройства — то есть в никуда. Звонок
"соединяется" визуально, но тишина — на любом типе связи одинаково, это не
баг звонка, это baseline для локальной сети. Чинится выставлением реального
LAN IP компьютера в `.env`.

**Требует того же ограничения, что и любой звонок на iOS:** работает только
пока приложение открыто на экране, до фазы 2 из D14 (нативный фоновый
аудио-мост).

Осталось на потом, не блокирует: рации (T320/мини-рации) сознательно не
участвуют в индивидуальных звонках (отдельный UDP-протокол прошивки,
не Socket.IO/MediaSoup) — решено первой версией не заниматься.

### D21. Временный пароль остаётся навсегда (разобрано 2026-08-24, ОТЛОЖЕНО осознанно)
Человеку при заведении выдаётся временный пароль — печатается на карточке и
раздаётся на руки. Сменить его **обычный пользователь не может**: форма смены
лежит в диспетчерском разделе, а у абонента экран — рация, ссылки туда нет.
Флаг `mustChangePassword` при заведении ставится, но **клиент его полностью
игнорирует** — никто не просит и не заставляет. То есть напечатанные пароли
живут вечно.

**Решение Eugene 24.08.2026 — не чинить.** Система закрытая, внутри
организации; бумажка выдаётся человеку в руки; потерялась — администратор
сбросит за десять секунд. Сам QR-код приглашения, который и так печатают и
пересылают, даёт не меньше. На процесс не влияет, приоритет — iPhone.

Это третий подряд случай, когда мы сознательно не чиним дефект без
пострадавшего (см. D19 и остаток D7 про `canShareLocation`).

**Если понадобится — вот готовый разбор, чтобы не начинать заново.**

Лучший путь: показывать экран смены пароля **сразу после входа**, если стоит
флаг. Он закрывает настоящий риск (бумажка в кармане), а не просто даёт
возможность сменить, которой никто не воспользуется. Вариант «настройки в экране
рации» отклонён именно поэтому.

⚠️ **Две дыры на сервере, без которых экран сломается:**

| Что происходит | Ставит `mustChangePassword`? |
|---|---|
| Заведение нового человека (`onboarding`) | да |
| Перевыпуск приглашения с новым паролем | да |
| **Сброс пароля администратором** (`POST /api/users/:id/reset-password`) | **нет** |
| **Смена пароля пользователем** (`POST /api/users/:id/change-password`) | **не снимает** |

Последняя строка критична: **не сняв флаг, человека спрашивали бы о смене при
каждом входе, вечно.** Предпоследняя означает, что пароль, назначенный админом
при сбросе, считается постоянным — хотя это такой же временный пароль,
продиктованный по телефону.

Обе правки — около четырёх строк. Плюс экран на клиенте. Оценка целиком: полдня.

**Заодно проверено и подтверждено (это работает правильно):** пароль хранится
bcrypt-хешем, исходный не знает никто — ни диспетчер, ни администратор, ни
заглянувший в базу. Восстановить нельзя, но заменить можно: сброс админом (с
обрывом всех сессий) или перевыпуск приглашения с новым паролем. Человек не
остаётся заперт.

### D18. Беззвучный входящий вызов на Android — ✅ РАЗОБРАНО 2026-08-21 (оказалось не багом)
Жалоба: на Redmi 9A (MIUI 12, Android 10) индивидуальный вызов в спящем режиме
приходил молча — экран входящего с «принять/отклонить» появлялся, вибрация
была, звука не было. На более новом телефоне звонит нормально.

**Причина оказалась одна и простая: громкость звонка на аппарате стояла в 0**
(`STREAM_RING streamVolume:0` при `Max:15`, `Muted:false`). Подняли громкость —
звонит штатно. Ошибки в коде нет.

**Ловушка, на которую стоит не попасться второй раз.** В logcat при КАЖДОМ
вызове на MIUI висит:

    W/MediaPlayer: Couldn't open content://0@settings/system/ringtone_cache
        at android.media.Ringtone.setUri(Ringtone.java:332)

Выглядит как причина, ею не является. MIUI отдаёт из `getDefaultUri()`
служебный адрес-кэш (в system-настройках `ringtone_cache = null`, реальный файл
лежит в настройке `ringtone`), но класс `Ringtone` это переживает: следом идёт
`D/Ringtone: Successfully created local player`, и играет запасной источник.
Предупреждение присутствует и в молчавшем звонке, и в нормально зазвонившем —
проверено на обоих логах. **Не диагностировать по нему.**

**Что сделано в коде:** добавлена одна строка в `PrivoxIncomingCallRinger`
(оба приложения) — предупреждение в лог при `STREAM_RING == 0`. Громкость
намеренно не поднимаем: беззвучный режим это выбор человека. Разбирательство
заняло час, с этой строкой заняло бы минуту.

**Что рассматривалось и ОТКЛОНЕНО:** переписать звонарь с `Ringtone` на
`MediaPlayer`. Писалось под неверный диагноз; `Ringtone` доказанно сам
справляется с подменой адреса на MIUI, а в самописной версии этот запасной путь
пришлось бы воспроизводить руками — и проверить его не удалось, MIUI не даёт
ставить сборку по USB (`INSTALL_FAILED_USER_RESTRICTED`, лечится пунктом
«Установка через USB» в меню разработчика). Раздавать всем пользователям
непроверенный самописный код воспроизведения звука ради гипотетической проблемы
— плохой размен.

### D19. «Звонок не зацикливается на Android 7–8.1» — ❌ НЕ ПОДТВЕРДИЛОСЬ 2026-08-23
Гипотеза была: в `PrivoxIncomingCallRinger` зацикливание и громкость стоят под
`if (SDK_INT >= P)`, а `Ringtone.setLooping()`/`setVolume()` появились только в
API 28 — значит на Android 7.0–8.1 рингтон играет один раз вместо 45 секунд.

**Проверено на живой T320 (Android 8.1, API 27) — гипотеза неверна.** Звонок
играет нормально всю положенную минуту. Замер `dumpsys audio`:

    23:24:33.133  player piid:71 state:started   USAGE_NOTIFICATION_RINGTONE
    23:25:17.885  releasing player piid:71       ← 44.7 с спустя

Плеер прожил ровно `MAX_RING_DURATION_MS`, и всё это время звучал (подтверждено
на слух — 45 секунд против 4 не спутать).

**Где была ошибка рассуждения:** появление ПУБЛИЧНОГО сеттера в API 28 не
значит, что поведения не было раньше. `Ringtone` зацикливал рингтоны внутри
себя и до 28-го; сеттер лишь дал приложению им управлять. Вывод общий: «метод
добавлен в API N» — не доказательство, что до N функциональности не было.

Ветку `if (SDK_INT >= P)` трогать не нужно, переписывание на `MediaPlayer` не
требуется. Оба варианта рассматривались и отклонены — см. D18.

**Попутно замечено, не чинится:** звонарь запускается дважды — сначала из
`PrivoxFirebaseMessagingService.onMessageReceived`, следом из
`IncomingCallActivity.onCreate`. Первый плеер создаётся и тут же выбрасывается
вторым вызовом (тот первым делом делает `stop()`), в логе это видно как
`piid:63` — создан и освобождён за 200 мс, не начав играть. Работе не мешает,
слышимого эффекта нет. Трогать рабочий код доставки вызовов ради косметики не
стоит.

### D17. Кнопка побудки на T320 слишком мелкая — ✅ СДЕЛАНО и проверено на рации 2026-08-23
Было: колокольчик и треугольник SOS стояли вплотную (`gap-2`) голыми значками
16×16 **без внутренних отступов** — область нажатия равнялась самому значку.

**Выбран первый из трёх предложенных путей — увеличить область и развести по
краям.** Решающий довод: приложение T320 тянет веб с сервера
(`capacitor.config.json` → `server.url = /radio`), поэтому правка интерфейса
доезжает до раций сразу, без пересборки APK и просьбы всем переустановиться.
Аппаратная клавиша 231 потребовала бы нативной правки, нового APK и отняла бы
вторую кнопку PTT.

Второй довод — несимметричная цена ошибки: не нажать побудку досадно, нажать
вместо неё SOS — ложная тревога у всей организации. Поэтому кнопки разнесены по
**противоположным** краям панели, чтобы промах физически не мог попасть в
соседнюю, а состояние канала переехало между ними.

| | Было | Стало |
|---|---|---|
Размеры замерены **на живой рации**, а не прикинуты по коду, и замер вскрыл то,
чего из кода не видно: у экрана T320 `devicePixelRatio = 0.75`, то есть прежние
16 CSS-точек занимали всего **12 физических** — примерно 1.8 мм. Проблема была
хуже, чем в описании.

| | Было | Стало (`p-3`) |
|---|---|---|
| Кнопка, физические точки | 12×12 (~1.8 мм) | **30×30 (~4.6 мм)** |
| Зазор между SOS и побудкой | 6 | **174** |
| Высота панели | ~24 (7% экрана) | ~37 (12%) |

Промежуточный вариант `p-2` (24×24, ~3.6 мм) тоже примеряли на рации; выбран
`p-3`: задача была про «трудно попасть пальцем», и 3.6 мм всё ещё меньше
половины комфортного размера. Плата — около строки списка. Добавлена подсветка
нажатия (`active:bg-…`): на рации важно понимать, что попал.

**Как примеряли, не выкатывая — пригодится снова.** В `capacitor.config.json`
стоит `webContentsDebuggingEnabled: true`, поэтому к webview рации можно
подключиться через CDP и подрисовать стили поверх работающей страницы:

    PID=$(adb -s <serial> shell pidof tech.privox.ptt)
    adb -s <serial> forward tcp:9222 localabstract:webview_devtools_remote_$PID
    curl -s http://localhost:9222/json     # взять webSocketDebuggerUrl вкладки /radio

Дальше `Runtime.evaluate` меняет стили, `adb exec-out screencap` снимает экран,
`location.reload()` возвращает всё как было. Так меряются реальные размеры в
физических точках — на глаз в 240×320 не угадать. Проброс порта отваливается
при перезагрузке страницы и переподключении кабеля, его надо ставить заново.

**Продолжение от Eugene (23.08):** увеличенной кнопки мало — «нажать пальцем
неудобно, хочу дойти крестовиной и нажать центральную». Резонно: у рации есть
физический D-pad, целиться пальцем в 30×30 на 240×320 незачем. Нижняя панель
включена в навигацию:

- **↓ с последней строки списка** уводит фокус в нижнюю панель (и из пустого
  списка тоже — иначе до неё было бы не добраться);
- **← / →** переключают между SOS и побудкой;
- **центральная (Enter)** нажимает;
- **↑ или Back** возвращают в список;
- смена вида (вход в группу, возврат назад) всегда сбрасывает фокус в список —
  иначе после «назад» человек жмёт центральную, ожидая выбрать группу, а
  попадает по панели.

**Осознанно:** при входе в панель фокус встаёт на **побудку**, а не на SOS.
Побудка — повседневное действие, а ложная тревога не должна быть в одном
небрежном нажатии центральной кнопки; до SOS надо шагнуть влево. Выбранная
кнопка подсвечивается рамкой, а в центре панели вместо статуса появляется
подсказка (`ALERT GROUP · OK` / `SOS · OK`) — на 240×320 объяснять управление
больше негде.

**Проверено на живой T320 после выкатки (Eugene): «всё работает по плану».**
Крестовина доходит до панели, подсветка и подсказка видны, центральная кнопка
жмёт побудку.

**Вывод на будущее, важнее самой правки:** первым решением было увеличить
кнопку (16 → 30 физических точек). Оно верное, но недостаточное — у рации есть
физический D-pad, и правильный ответ был «не целиться пальцем вообще». Когда
задача звучит как «трудно попасть пальцем», стоит сперва спросить, нужен ли
здесь палец, а не только насколько увеличить цель.

### D16. Маршрутизация звука — ✅ СДЕЛАНО для Android 2026-08-21, iOS остаётся
Хочется: групповой канал звучит громко (динамик), а индивидуальный дуплекс-
звонок (D15) — тихо "к уху", как обычный телефонный разговор.

Нашли причину и объём работы в `android/t320/.../MainActivity.java:45-127`:
браузер/WebView сам переводит устройство в `MODE_IN_COMMUNICATION`, как только
одновременно активны микрофон и воспроизведение — а это **по умолчанию
направляет звук в тихий наушник**, не на динамик. Для T320 это принудительно
перебивают через `AudioManager.setSpeakerphoneOn(true)` каждые 1500мс
(`forceSpeakerphone()`), потому что рации нужен громкий звук всегда.

У обычного Android-приложения (`android/phone/`) такого принудительного
переключения нет вообще — вероятно, **групповой канал на телефоне уже сейчас
тихий**, если это не проверялось отдельно. Индивидуальный звонок, скорее
всего, и так уже "к уху" без доработок — именно так ведёт себя браузер по
умолчанию.

Что нужно, когда возьмёмся: для `phone`-приложения включать
`forceSpeakerphone()` (по образцу T320) только пока активен групповой канал,
и не включать во время индивидуального звонка — то есть веб-код должен
как-то сообщать нативному Android-слою, в каком он режиме (небольшой
Capacitor-плагин/мост, аналогично уже существующему `PrivoxPushPlugin`).
Для iOS аналогичного нативного кода пока нет вообще — понадобится отдельно
писать через `AVAudioSession.overrideOutputAudioPort`, только когда дойдём
до нативной iOS-разработки (см. D14).

**Сделано 2026-08-21:** нативный плагин `PrivoxAudio` в обоих Android-проектах.
Групповой канал — динамик, личный звонок — наушник, плюс ручное переключение
в шапке и на экране звонка. Маршрут переустанавливается по таймеру: браузер
сбрасывает его на каждом включении микрофона.

Ключевая находка: `setSpeakerphoneOn()` **на Android 12+ работает наполовину**
— динамик включает, а наушник не возвращает. Отсюда две ветки: на новых
версиях устройство вывода выбирается явно через `setCommunicationDevice()`.
Без этого на Android 15 всегда оставался динамик, на Android 10 всё работало —
именно так проблема и проявилась.

У T320 собственный цикл держал динамик всегда; теперь он отступает, когда
плагин просит наушник.

### D22. iOS: убрать иконку-заглушку — ✅ СДЕЛАНО 2026-08-25
`ios/phone/App/App/Assets.xcassets/AppIcon.appiconset/` содержал дефолтную
заглушку Capacitor. Заменена на тот же дизайн, что уже в проде на Android
(`android/phone/.../mipmap-xxxhdpi/ic_launcher.png` — тёмный бейдж, зелёный
градиентный микрофон, волны).

**Технически проще, чем ожидалось.** Современный формат `Contents.json`
Capacitor 8 требует **только один** файл — `"idiom": "universal", "size":
"1024x1024"`, без сетки размеров под каждый слот (Xcode масштабирует сам).

512×512, с альфа-каналом и уже вписанными скруглёнными углами). iOS требует
**полностью непрозрачный** квадрат без альфа-канала — прозрачные углы
плющились бы в чёрный на реальном устройстве.

Сведено одной командой ImageMagick (`brew install imagemagick`, локально не
было): `magick icon-512.png -background "#0A0C0A" -flatten -resize
1024x1024 -alpha off out.png` — `#0A0C0A` это `ptt-dark` из
`tailwind.config.js`, тот же тон, что уже залит внутри скруглённого квадрата
исходной иконки, поэтому расплющенные углы сливаются с фоном без видимого
шва. Результат подставлен как `AppIcon-512@2x.png` (имя файла не менялось,
чтобы не трогать `Contents.json`).

Пробовали сначала взять `web/public/icons/privox-ptt-icon.svg` для более
чёткого рендера без апскейла — отклонено: это старый плоский набросок без
тёмного бейджа/градиента, визуально не совпадает с уже опубликованной
Android-иконкой. `icon-512.png` — правильный источник истины для фирменного
вида, апскейл 512→1024 на таком простом векторном рисунке незаметен на глаз.

**✅ Проверено на реальном iPhone 2026-08-27 (Eugene): «иконка хорошая».**

Дополнительно к завтрашнему пункту — вся нестабильность CallKit-звонка,

**Осталось для iOS:** тот же смысл через `AVAudioSession.overrideOutputAudioPort`

экспонирует "динамик" отдельно от "наушника" на мобильных браузерах.

### D24. Экран ANSWER/DECLINE не гаснет сам после звонка — ✅ ПОЧИНЕНО 2026-08-25 (ждёт живой проверки)
Воспроизводилось стабильно (2/2) на iPhone: после завершённого через CallKit
разговора карточка входящего звонка (`ANSWER`/`DECLINE`) оставалась висеть.
Первая гипотеза («это был отдельный повторный вызов во время теста») не
подтвердилась — Eugene явно повторил чистый эксперимент дважды, надпись была
оба раза.

**Настоящая причина, подтверждена чтением кода.** Карточка ANSWER/DECLINE
(`alerts` в сторе, `variant: 'user-call'`, добавляется в
`web/src/hooks/useSocket.ts:198` по живому socket-событию
`user-call-incoming`) убиралась **только одним способом** — нажатием кнопки
ANSWER/DECLINE прямо на ней (`AlertPanel.tsx` → `markAlertRead(alert.id)`).
Больше нигде в коде не было ни одного вызова, чистящего alert по `callId`.

На iOS звонок нередко приходит **двумя параллельными каналами**: обычным
живым сокетом (создаёт эту самую карточку, как на Android/в браузере) и
VoIP-пушем (поднимает нативный экран CallKit). Если человек отвечает через
CallKit (слайдер), весь дальнейший путь — `useNativePush.ts:consumePendingCall`
→ `setActiveCall(...)` напрямую — идёт **в обход `AlertPanel` целиком**.
Нажимать было некому, карточка виснет навсегда (до вытеснения лимитом в 50
алертов или ручного клика на другой странице).

**Исправление:** новое действие стора `markCallAlertRead(callId)`
(`web/src/store/useStore.ts`) — чистит alert по `callId`, а не по `id`
самого алерта (который вызывающему коду и не известен). Вызывается из всех
путей, разрешающих звонок в обход `AlertPanel`:
- `useSocket.ts` → `call-connected` и `call-ended` (обычный дуплекс-звонок,
  D15, для всех платформ);
- `useNativePush.ts` → `consumePendingCall()` в ветке
  `kind:'user' && responseStatus:'answered'` (короткий путь восстановления
  `activeCall` из данных push, см. D14);
- `useNativePush.ts` → подписка `callEndedNatively` (разъединение с
  нативного экрана CallKit, см. фикс от 25.08 выше).

**Заодно нашли и починили смежный баг того же класса, для отказа, а не
ответа.** Тот же `consumePendingCall()` при `kind:'user' &&
responseStatus:'declined'` (отклонили звонок слайдером на CallKit, сервер уже
уведомлён через `CallResponseReporter`) проваливался в общий блок ниже,
который **заново показывал ANSWER/DECLINE** для уже отклонённого звонка и
тянул человека на `/radio` — спор с уже принятым решением. Добавлен ранний
выход: для этой комбинации только чистим alert по `callId`, ничего не
показываем и никуда не ведём.

Убрана диагностическая `console.log`, добавленная для отладки этого случая
(была лишней, как только причина нашлась чтением кода, а не логами).

**Проверено вживую 25.08.2026 (Eugene): «карточка ANSWER/DECLINE вроде
исчезла».** Проверялось попутно с тестом фикса односторонней тишины (см.
апдейт в D14) — полного отдельного прогона (в т.ч. отклонение звонка с
блокировки) пока не было, но по основному сценарию (звонок → ответ через
CallKit → разговор → hangup) карточка больше не виснет.

### D25. 🟡 Практически снято через D36 (техническое ограничение осталось) — перевыпуск приглашения привязан к группе, а не ко всему аккаунту (замечено 2026-08-26)

конкретной группы даёт токен, ведущий только в **эту одну** группу
(`info.group` в ответе `/api/invites/<token>` — одно значение, не список).

**Возражение Eugene, зафиксировать дословно:** «это не логично, я даю логин
и пароль для абонента, а не только члена группы. если он состоит в

По факту это не баг и не блокирует ничего прямо сейчас — у логина/пароля
уже и так нет этого ограничения: вход по `/login` восстанавливает доступ
сразу ко всем группам абонента, потому что учётные данные привязаны к
аккаунту целиком, а не к отдельному членству. QR/инвайт — это просто более
быстрый путь для одной конкретной группы (типично: онбординг новичка в
одну конкретную группу), и в этом сценарии текущее поведение осмысленно.

Открытый вопрос на будущее, если возьмёмся: должен ли **перевыпуск
приглашения существующему участнику нескольких групп** (в отличие от
исходного онбординга новичка в одну группу) генерировать один токен,
который при активации восстанавливает членство сразу во всех группах
человека — а не только в той, с чьей карточки перевыпустили. Потребует
решить, что показывать на странице `/join/<токен>` в этом случае (сейчас
UI жёстко рассчитан на один `group.name`) — список групп вместо одной,
или просто «добро пожаловать обратно, <позывной>» без привязки к группе
вовсе. Не начинать без отдельного решения по UX.

**🟡 Апдейт 2026-08-30, после D36:** само техническое ограничение (один
QR-токен = одна группа) никуда не делось, но D36 даёт практический обход —

принципиально неизвестен и карточка — чисто QR. Не начинать без отдельного
решения по UX, как и раньше.

### D31. Вложения в сообщениях — видео не поддерживается, лимит фото мал (замечено 2026-08-28)
Eugene сообщил: текст в чате идёт нормально, а с фото и видео проблема.
Проверено по коду, две причины подтверждены точно, одна — гипотеза:

1. **Видео не поддерживается вообще, ни на клиенте, ни на сервере.**
   Белый список типов на сервере (`server/src/routes/messages.ts`,
   `allowedAttachmentTypes`/`attachmentTypesByExtension`) не содержит ни
   одного video-MIME — любое видео получает `415`. На сайте диалог выбора
   файла (`accept="image/*,application/pdf,..."`) тоже не предлагает видео
   вообще — не баг, а просто никогда не было сделано.
2. **Лимит фото — 10 МБ** (`maxAttachmentSize`), а современные телефоны
   часто снимают на 15-25 МБ (HEIC, 48-мегапиксельные камеры) — вероятная
   причина жалобы именно на фото. Клиент честно показывает ошибку про
   размер, но на сервере есть смежный дефект: если лимит превышен по
   другой причине (`PayloadTooLargeError` от `express`), `errorHandler.ts`
   не распознаёт эту ошибку и отдаёт generic `500` вместо понятного
   сообщения про размер файла.
3. **Не проверено, гипотеза:** `web/nginx.conf` не задаёт увеличенный
   `proxy_read_timeout`/`proxy_send_timeout` для `/api/` (дефолт nginx —
   60с), тогда как клиентский axios-таймаут на аплоад — 120с. На слабой
   рационной связи загрузка большого файла может обрываться на уровне
   nginx раньше, чем сдастся сам клиент — текстовые сообщения этой
   проблемы не имеют, они всегда маленькие. Требует проверки логов
   nginx/сервера на 504 при реальных жалобах, прежде чем чинить вслепую.

**✅ Частично исправлено 2026-08-28** (пункты 2 и generic-500, видео — нет):

  `server/src/routes/messages.ts` (`maxAttachmentSize`),
  `web/src/pages/messages/MessengerPage.tsx` (клиентская проверка + текст
  ошибки), `web/nginx.conf` (`client_max_body_size 26m`).
- `errorHandler.ts` теперь узнаёт `PayloadTooLargeError` (413) и отдаёт
  понятное `"File is too large"` вместо generic `500`.
- Заодно поднят `proxy_read_timeout`/`proxy_send_timeout` для `/api/` до
  130с (было — дефолт nginx 60с) — закрывает гипотезу №3 про обрыв на
  слабой связи, даже не дожидаясь подтверждения по логам.
- **Видео по-прежнему не поддерживается** — не начато, требует отдельного
  решения (добавить video-MIME в белый список на сервере + `accept` на
  клиенте, подумать про отдельный больший лимит для видео).

### D39. ✅ СДЕЛАНО 2026-08-31 — красный бейдж на иконке iOS не сбрасывался после прочтения
Вторая запись в форме тестировщиков (`reference-privoxptt-ideas-form`) — от
Eugene, «Реально важно»:

> «На иконке после неотвеченных вызовов или сообщений, точно не ясно чего,
> остаётся красная метка с цифрой не прочитанных или не обработанных
> оповещений. После прочтения сообщений не исчезает».

**Причина, подтверждено по коду:** сервер выставляет `aps.badge` на каждый
push о сообщении (`sendIosMessagePush`, D27 3/4, вчера) — но нигде в iOS-
клиенте не было ни единого места, которое сбрасывает бейдж обратно. iOS
просто держит последнее полученное число бесконечно, пока приложение само
явно не попросит его обнулить — само по себе оно никогда не гаснет.
Пропущенные звонки на бейдж не влияют (`scheduleMissedCallNotification` не
выставляет `badge` вообще) — источник ровно один.

**Исправлено:** `AppDelegate.swift` → `applicationDidBecomeActive` (был
пустой заглушкой) теперь вызывает `UIApplication.shared.
applicationIconBadgeNumber = 0` — бейдж сбрасывается при каждом выходе
приложения на передний план. Собрано (`xcodebuild ... BUILD SUCCEEDED`) и
загружено в TestFlight как **build 8**.

**🔴 Не сработало на живом устройстве (iOS 18.7), проверено вживую
2026-08-31:** бейдж так и остался висеть после реального открытия
приложения. Причина: `applicationIconBadgeNumber` объявлен устаревшим
Apple ещё в iOS 17 в пользу `UNUserNotificationCenter.setBadgeCount()`, и
на практике оказался не просто "не одобряемым", а реально ненадёжным на
современных версиях iOS, не только формально устаревшим.

**✅ Исправлено окончательно:** `applicationDidBecomeActive` теперь
использует `UNUserNotificationCenter.current().setBadgeCount(0)` на iOS 17+
(с проверкой `#available`), со откатом на старый API только для iOS 15-16.
Собрано, загружено как **build 9**.

**🔴 Опять не сработало на живом устройстве, проверено вживую 2026-08-31**
(билд 9 подтверждён в TestFlight) — бейдж всё ещё не гас. Настоящая
причина оказалась не в самом API вообще: приложение сценовое
(`SceneDelegate`, нужен для Universal Links) — а у сценовых приложений
`AppDelegate.applicationDidBecomeActive` **не вызывается вообще**, Apple
перенесла этот момент жизненного цикла в `UIWindowSceneDelegate.
sceneDidBecomeActive(_:)`. Код обеих попыток был синтаксически верным —
просто ни разу не выполнялся.

**✅ Исправлено (действительно) окончательно:** сброс бейджа перенесён в
`SceneDelegate.swift` → `sceneDidBecomeActive(_:)` (тот же `setBadgeCount`/
`applicationIconBadgeNumber` в зависимости от версии iOS, просто в
правильном месте). `AppDelegate.applicationDidBecomeActive` оставлен пустым
с комментарием, почему — на случай, если кто-то попробует чинить бейдж там
снова. Собрано, загружено как **build 10**. Не проверено вживую — ждёт
теста.

### D40. ✅ СДЕЛАНО 2026-08-31 — сообщения: непрочитанные не выделяются визуально, нет статуса "доставлено/прочитано" (идея Eugene, 2026-08-31)

  создания строк `MessageRead` для 1:1-диалога шлёт `message:read` через

  `{ userId }` (кто прочитал) — чтобы галочки у отправителя обновлялись
  живьём, без обновления страницы.

- `web/src/store/useStore.ts`: вместо разрозненных мест, вручную

  <userId, count>` (только для личных диалогов). Плюс `incrementDirectUnread
  (userId)` — точечный инкремент конкретного собеседника при `message:new`

### D43. ✅ СДЕЛАНО 2026-08-31 — личное сообщение от привилегированной роли (SUPERADMIN/ADMIN/DISPATCHER) человеку не из общей группы уходило в никуда
Eugene, живой тест: «супер админ может послать сообщение личное кому
хочет, но у абонентов в списках нет супер админа, потому сообщение уходит
в никуда и прочитать его нельзя». Уточнил — у диспетчера та же беда:
пишет лично абоненту, тот получить/прочитать не может.

**Причина:** `directContactFilter()` в `server/src/routes/messages.ts`
использовался как для отправки, так и для списка диалогов/чтения, но
считался ВСЕГДА от роли текущего смотрящего. Когда привилегированная роль
(SUPERADMIN/ADMIN/DISPATCHER) пишет — проверка со стороны отправителя не
ограничена (может писать кому угодно в организации). Но когда ПОЛУЧАТЕЛЬ
(обычный USER) открывает `GET /messages/conversations`, тот же фильтр
считался уже от РОЛИ ПОЛУЧАТЕЛЯ — а для обычного USER условие было
"показать только тех, с кем есть общая группа". Если отправитель
(например, SUPERADMIN) физически не состоит участником ни одной группы
с этим получателем — сообщение реально сохранялось в базе, но не
попадало ни в список диалогов, ни в счётчик непрочитанных, и `GET
/messages`/`POST /read` тоже отказывали в доступе (403) — переписка
существовала, но была невидима и недоступна для получателя.

**Фикс:** `directContactFilter()` теперь дополнительно разрешает доступ
(и на чтение, и на ответ), если между текущим пользователем и целевым
уже ЕСТЬ переписка — проверка через relations `sentMessages`/
`receivedMessages` на модели `User` (`OR` к прежнему условию "общая
группа"). Это НЕ открывает холодный старт переписки в обход общих групп
(если сообщений ещё не было и общей группы нет — доступ по-прежнему
закрыт), только чинит уже начатую кем-то привилегированным переписку —
получатель теперь видит её в списке, может прочитать и ответить.
`tsc --noEmit` на сервере — чисто. **Не проверено вживую** — ждёт теста
(сообщение от SUPERADMIN/DISPATCHER человеку не из общей группы: должно
появиться в списке диалогов получателя, открываться и допускать ответ).

### D46. Скачивание файлов в чате может не работать в iOS-приложении (найдено 2026-08-31, не проверено вживую)
Eugene спросил, как сохраняются полученные в чате файлы (не голосовые,
обычные вложения — фото/PDF/документы). Проверено по документации
WebKit, не вживую на телефоне: `MessageAttachment.download()`
(`web/src/pages/messages/MessengerPage.tsx`) скачивает через
`<a download>` с `blob:`-ссылкой — а это **подтверждённый, незакрытый
баг WebKit**: WKWebView (движок нашего iOS-приложения, НЕ обычный Safari
в браузере) не поддерживает `blob:` в `href` у `<a download>`
(bugs.webkit.org/show_bug.cgi?id=216918). На компьютере и в Android
должно работать нормально (обычная загрузка в браузере) — вопрос именно
про установленное iOS-приложение из TestFlight.

**Подтверждено вживую и починено 01.09.2026.** Eugene отправил Максу PDF
со своего iPhone — файл не скачивался; с компьютера тот же файл качался
нормально, то есть на сервере он лежал целым и получателю доходил.
Диагноз выше оказался верным полностью.

**Нативная правка НЕ понадобилась.** `WKDownloadDelegate` — не
единственный путь: `navigator.share` с файлом (Web Share API level 2)
работает внутри WKWebView и открывает системную шторку iOS, откуда есть
«Сохранить в Файлы». Это чистая правка веб-кода, а значит доезжает до
установленного приложения сразу после выкатки, без Xcode, без новой
сборки TestFlight и без ожидания Apple. Прежнее скачивание через
`<a download>` оставлено запасным путём, поэтому на компьютере и в
Android ничего не изменилось.

Заодно убрано молчание: отказ сервера раньше проходил бесследно и
выглядел как мёртвая кнопка — теперь под файлом появляется сообщение.
Блоб запоминается между нажатиями, потому что `navigator.share` на iOS
требует вызова по жесту.

Логика прогнана по пяти сценариям (шторка открылась с верным файлом;
отмена человеком — тишина; иной отказ — откат на скачивание; компьютер —
как раньше; ошибка сервера — видимое сообщение).

⚠️ **Ждёт подтверждения на живом iPhone.** Отсюда шторку не проверить:
Safari Web Inspector есть только на MacBook. Если окажется, что с первого
нажатия шторка не выходит, а со второго выходит — iOS сочла жест
остывшим, пока качался файл, и нужно подкачивать блоб заранее.

### D48. Чат уезжал за край экрана на телефоне (сделано 01.09.2026, на проде)
В одном личном чате диалог сместился вправо, вложение не открывалось, а
кнопка отправки ушла за экран. Ломался ровно один чат — остальные были в
порядке, и это была главная подсказка.

Причина не в содержимом и не в непрочитанных: у элемента `grid`
минимальная ширина по умолчанию равна **min-content, то есть самому
длинному неразрывному слову во всей переписке**. У колонки со списком
чатов (`aside`) `min-w-0` стоял, у колонки с перепиской (`section`) —
нет. В тот чат прислали длинную ссылку, колонка стала шире экрана и
утащила вправо всё, включая строку ввода.

Вторая половина той же ловушки, на которую легко наступить повторно:
`break-words` здесь бесполезен. `overflow-wrap: break-word` слово
переносит, но **min-content не уменьшает** — ширину оно всё равно
требует. Работает только `anywhere`, он и стоит теперь у тела сообщения.

Проверено на копии разметки шириной 390px: было 476px и правый край
кнопки на 464px (за экраном), стало 390px и 378px.

### D49. Пять новых продуктовых идей от Streltcoff, "инциденты + датчики" (форма тестировщиков, 2026-09-03)
Все помечены «Просто идея», платформа «Do not know» — не баги, а
предложения по развитию. Не начато, требует обсуждения приоритета с
Eugene перед стартом любого из пунктов.

**1. Инцидент-ядро с обязательным подтверждением реакции.** У тревоги
(от датчика ИЛИ от сотрудника) появляется ответственный из группы,
обязанный отреагировать (принял/проверил/снял), логируются время тревоги
и время реакции, эскалация при отсутствии ответа. Дополнительно —
отправка информации об инциденте администратору на почту/в другой
мессенджер через webhook. Пример от автора: «Fridge 12: 9.4°C, выше
диапазона 7 минут, ждём ack, эскалация через 3 мин» → «Иван: принял, ETA
12 минут». Самая крупная из пяти идей — фактически новая сущность
"инцидент" поверх существующих `Sensor`/тревог, с полноценным
жизненным циклом (создан → назначен → принят → закрыт/эскалирован).

**2. QR как замена/дополнение датчика для обходов.** Сотрудник при
физическом обходе объекта сканирует QR-код на контрольной точке —
подтверждение присутствия без установки настоящего датчика в каждой
точке.

**3. Рация как мобильный BLE-шлюз для чужой телеметрии.** Устройство в
машине техника, проезжая мимо торговых автоматов/локеров/зарядных
станций, собирает их телеметрию по BLE и передаёт на сервер
(store-and-forward) — оператору сети автоматов не нужен свой SIM/шлюз в
каждой точке, плюс диспетчер получает подтверждение, что техник
действительно объехал точки маршрута.

**4. Датчик парковки + рация инспектора.** Занятость парковочных мест
передаётся через рацию проверяющего инспектора на сервер — видно, когда
и сколько мест простаивает; сверка с логом оплат позволяет проверять
корректность работы самого инспектора.

**5. Периодические отчёты владельцу.** Настраиваемый под компанию
email/мессенджер-отчёт (день/неделя): активность сотрудников,
срабатывания датчиков, время реакции на инциденты, повторные тревоги.
Логически продолжает идею 1 — отчёты по сути показывают накопленную
статистику по инцидент-ядру.

### D51. Фоновая геолокация с оповещением "абонент прибыл в точку А" (вопрос Eugene, 2026-09-05)
Идея из той же встречи, что и D50: диспетчер получает сигнал, когда
абонент физически прибыл в заданную точку/зону — полезно, например, для
сценария "мобильный техник объезжает точки" (см. идею 3 в D49).

**Проверено по коду — сейчас невозможно в принципе, не просто
не хватает функции.** `web/src/hooks/useGeolocation.ts` использует
обычный браузерный `navigator.geolocation.watchPosition()` — это
работает ТОЛЬКО пока страница/вебвью активна на экране. То же самое
системное ограничение WKWebView, что уже задокументировано в D14
(фон замораживает JS) — на iOS сейчас нет вообще никакого GPS-сигнала,
как только приложение свёрнуто. По Android отдельного нативного
фонового геосервиса тоже не заведено — вероятно, то же самое
ограничение (не проверено на живом устройстве).

**Не начато.** Технически решаемо, но требует настоящей нативной
работы на каждой платформе, не веб-правки:
- **iOS** — `CLLocationManager` geofencing (region monitoring):
  система сама будит приложение на вход/выход из зоны даже когда оно
  закрыто, аппаратный GPS с низким энергопотреблением. Требует
  разрешение "Always" (более строгий запрос, чем текущее "во время
  использования").
- **Android** — Geofencing API (Google Play Services) или
  foreground-сервис с фоновым разрешением на геолокацию (тоже отдельный,
  более строгий запрос на современных версиях Android).
- Рации (T320) — не проверено, но вероятно менее критично: рация обычно
  и так постоянно активна, не "сворачивается" пользователем как
  обычный телефон.

Не начинать без отдельного решения по приоритету — сравнимо по объёму
с нативной частью D14 (CallKit), не мелкая правка.
