# iPhone: звонок на спящий телефон — состояние и передача на MacBook

Задача от Eugene: телефон лежит в кармане, в сумке, ночью на столе; человек в
другом приложении или экран погашен — а руководителю срочно нужно собрать всю
группу. На Android это уже работает через FCM. Здесь — то же самое для iPhone.

## Что это даёт и чего не даёт

**Даёт:** VoIP-push поднимает iPhone даже из выгруженного состояния, показывает
**нативный полноэкранный входящий звонок**, человек отвечает — и он в эфире.

**Не даёт:** слышать эфир, НЕ отвечая на вызов, и говорить со свёрнутым
приложением. Это отдельная большая работа (Apple PushToTalk Framework, нативный
звук в обход WebView) — начинать её только после решающего опыта, см. в конце.

## Сделано на сервере — и как проверено

| | |
|---|---|
| `server/src/services/apns.ts` | Отправка в APNs напрямую: HTTP/2, авторизация JWT (ES256, ключ `.p8`), переиспользование токена, разбор причин отказа, закрытие мёртвых токенов |
| `server/src/services/push.ts` | Звонок уходит в **два канала**: Android — FCM, iPhone — VoIP-push. Отказ одного не отменяет второй |
| `Device.voipToken` | Новое поле. Токен PushKit — это **не** обычный push-токен, они адресуются раздельно |
| `Device.pushToken` | Стал необязательным: iPhone может зарегистрироваться, имея пока только VoIP-токен |
| `POST /api/devices/register` | Принимает `voipToken`; ищет устройство по любому из токенов, чтобы один аппарат не завёлся дважды |
| Рассылка датчиков | Ограничена Android явно. Раньше туда попадали все платформы, и токен APNs ушёл бы в Firebase, который его отвергает |

**Проверено против живых серверов Apple** (24.08.2026, отправка на выдуманный
токен устройства):

    ответ APNs: {"ok":false,"status":400,"reason":"BadDeviceToken"}

Это лучший возможный ответ на данном этапе: Apple приняла соединение, **подпись
JWT**, тему `tech.privox.ptt.voip` и тип `voip` — отвергла только сам токен, а он
и был выдуманный. Если бы подпись была неверна, ответ был бы `403
InvalidProviderToken`.

Непроверенной остаётся **только доставка на живой iPhone** — для неё нужна
нативная часть.

Плюс 6 модульных тестов (`apns.test.ts`) на составление темы и разбор причин
отказа — это те места, где ошибка была бы незаметной.

## Настройки — и где именно они нужны

**Push отправляет БОЕВОЙ сервер.** Приложение на iPhone ходит на
`https://ptt.privox.tech`, значит звонок ему шлёт прод, а не машина
разработчика. Настройки APNs обязательны **в Coolify**.

Ключ можно отдать двумя способами:

| | Где применяется |
|---|---|
| `APNS_KEY` — содержимое `.p8` целиком | **Прод.** В контейнере файлов нет, секреты приходят переменными окружения — как `FIREBASE_SERVICE_ACCOUNT_JSON` рядом |
| `APNS_KEY_PATH` — путь к файлу | Машина разработчика, где файл лежит на диске |

Заданы оба — содержимое приоритетнее. Переносы строк в переменной могут прийти
как литеральные `\n` (так их сохраняют Coolify и docker) — код это разворачивает.

Готовые значения для вставки в Coolify: `~/PrivoxKeys/apns-coolify-env.txt`.

Локально (`server/.env`):

    APNS_KEY_PATH=/Users/<пользователь>/PrivoxKeys/AuthKey_723D52BFNL.p8
    APNS_KEY_ID=723D52BFNL
    APNS_TEAM_ID=2ND5G88WGD
    APNS_BUNDLE_ID=tech.privox.ptt
    APNS_ENV=sandbox

⚠️ **`APNS_ENV` — главная ловушка.** Сборка из Xcode на устройство ходит в
**sandbox**, TestFlight и App Store — в **production**. Ключ годен для обоих, но
АДРЕСА РАЗНЫЕ, и push, отправленный не туда, просто молча не доходит. При
переходе на TestFlight не забыть переключить.

⚠️ Файл `.p8` **не в git**. При переезде на MacBook скопировать вручную вместе с
остальными секретами (см. раздел 3 в `WORKSTATION_SETUP.md`).

### Находки по дороге — держать в голове при следующих правках

- **`SceneDelegate.swift` создаёт корневой контроллер в коде**
  (`window?.rootViewController = MainViewController()`), **Main.storyboard в
  этом не участвует вообще.** Была потрачена куча времени на правку
  `customClass` в storyboard — она ни на что не влияла. Если понадобится
  что-то ещё завязать на "приложение загрузилось" — редактировать
  `SceneDelegate.swift`/`MainViewController.swift`, не storyboard.
- **Гонка состояний "ответил, но не подключилось".** Статус "answered" уходит
  с сервера по живому Socket.IO (`call-connected`) в момент, когда WebView на
  телефоне ещё даже не начал грузиться (сокет не подключён) — событие
  теряется без следа, не буферизуется. Правка в
  `web/src/hooks/useNativePush.ts`: при `kind: 'user' && responseStatus:
  'answered'` состояние `activeCall` восстанавливается **локально из данных
  самого push** (добавлено поле `fromUserId` по всей цепочке
  push.ts → AppDelegate → PendingCallStore → PrivoxPushPlugin → JS), не
  дожидаясь повторной доставки события, которой не будет.
- **`print()` не виден нигде, если процесс запущен не из-под Xcode.**
  `xcrun devicectl device process launch` работает, но stdout процесса не
  долетает ни до `idevicesyslog`, ни до Console.app (оба ловят только
  системные демоны на современной iOS). Диагностика печатью работает
  ТОЛЬКО через прямой Run из Xcode (⌘R) с подключённым дебаггером — консоль
  внизу окна.
- Заблокированный экран отключает Xcode/`devicectl`/Console.app от
  устройства — отладка (логи, `devicectl process launch`) требует
  разблокированного телефона. Сама доставка push/показ CallKit-экрана этому
  не подчиняется — работает и на блокировке, просто не понаблюдать вживую.

### Разъединение — ✅ ПОЧИНЕНО и проверено живьём 25.08.2026

Найдено в живом тесте: приложение и CallKit не были связаны в обе стороны.
- Кнопка HANG UP внутри приложения гасила только наш WebRTC-разговор —
  системный экран CallKit (зелёная "трубка" в статус-баре) оставался висеть.
- Если разъединялся **собеседник** первым — сервер шлёт `call-ended` по
  сокету, а обработчик только чистил `activeCall` в сторе, не трогая CallKit
  вообще — трубка точно так же не гасла.

Оба направления связаны через `CXCallController`
(`PrivoxPushPlugin.endCall()` ↔ `CXEndCallAction`, см. `AppDelegate.swift`).
По пути починены два смежных бага: `endCall` дёргал `UIApplication.shared.
delegate` не на главном потоке (Main Thread Checker ловил это) — обёрнуто в
`DispatchQueue.main.async`; и `endCall` пытался погасить CallKit-сессию для
звонков, которые туда никогда не попадали (пришли обычным сокетом, пока
приложение было на переднем плане) — добавлена проверка
`AppDelegate.isKnownToCallKit(uuid)` перед обращением к `CXCallController`.

Проверено вживую несколько раз подряд: и когда разъединяется iPhone, и когда
разъединяется собеседник — трубка гаснет сама в обоих случаях.

### Односторонняя тишина при ответе через CallKit — найдено и исправлено 25.08.2026 (не проверено вживую)

Живой тест: Android звонит на iPhone (дуплекс, D15) — iPhone слышит Android
нормально, но **сам не передаёт ни звука**, независимо от того, был экран
разблокирован заранее или ответили со свёрнутого/заблокированного. Обратная
комбинация (iPhone звонит, Android отвечает) и Android-Android — работают
в обе стороны. Значит дело не в маршрутизации Android (`PrivoxAudioPlugin`
тут ни при чём) и не в mediasoup-сигналинге (проверено — код полностью
симметричен для caller/callee, см. `useWebRTC.ts`, `server/src/mediasoup/
router.ts`) — тишина именно в том, что **iPhone-callee не производит свой
аудио-трек**, хотя как caller — производит без проблем.

**Причина:** `AppDelegate.swift` реализовывал `CXProviderDelegate`, но не
реализовывал `provider(_:didActivate: AVAudioSession)`/`didDeactivate:`.
Это не опция, а часть контракта CallKit: система держит `AVAudioSession`
под своим контролем на время входящего звонка и должна явно передать право
её настроить и включить приложению именно через `didActivate` — без этого
колбэка сессия остаётся в session category CallKit по умолчанию, не
настроенной на запись. Внешне это выглядит как рабочий звонок (сигнализация,
ICE/DTLS, WKWebView получает трек с микрофона) — реальные сэмплы в трек
просто не пишутся. У caller эта проблема в принципе не может возникнуть:
исходящий звонок никогда не проходит через `CXProvider` вообще.

**Почему не всплывало раньше:** эта конкретная комбинация ролей (Android
звонит, iPhone отвечает через CallKit) не была подтверждена рабочей ни разу
до 25.08 — всё предыдущее тестирование сфокусировано на "iPhone отвечает",
но без надёжного контроля, кто именно был на другом конце и не терялась ли
разница между caller/callee на слух.

**Исправление** (`AppDelegate.swift`, `import AVFoundation` + два новых
метода `CXProviderDelegate`):
```swift
func provider(_ provider: CXProvider, didActivate audioSession: AVAudioSession) {
    try? audioSession.setCategory(.playAndRecord, mode: .voiceChat, options: [.allowBluetooth, .defaultToSpeaker])
    try? audioSession.setActive(true)
}
func provider(_ provider: CXProvider, didDeactivate audioSession: AVAudioSession) {}
```
Собирается чисто (`xcodebuild ... -sdk iphonesimulator` → `BUILD SUCCEEDED`).

**✅ Проверено вживую 25.08.2026 (Eugene): «заработало».** Android звонит на
iPhone — обе стороны слышат друг друга. Гипотеза подтвердилась полностью.

**Осталось непроверенным:**
- После "Ответить" иногда (не в каждой попытке) приложение само не выходит на
  передний план — остаётся системный экран звонка. Похоже на гонку в самой

- ~~Групповой "будильник" (`kind: 'group'`) через CallKit ещё не
  тестировали живьём~~ — по словам Eugene (26.08.2026) тоже отработал, без
  детального прогона/лога — закрепить отдельным тестом при случае.
- ~~Замечен зависший экран ANSWER/DECLINE после звонка~~ — причина найдена,

## Что уходит на серверы Apple — решено 24.08.2026

Вопрос Eugene: не пострадает ли конфиденциальность переговоров и переписки.

**Голос через Apple не идёт вообще** — разговор идёт напрямую через наш
mediasoup-сервер, push это только сигнал «зазвони». **Переписка тоже не идёт** —
сообщения живут только на нашем сервере и в push не попадают.

Через APNs транзитом проходит одно уведомление о звонке:

    callId, fromUserId, fromCallsign, fromDisplayName,
    groupId, groupName, createdAt, responseToken, responseUrl, kind

То есть Apple видит, кто кому звонит, позывной, имя и название группы. Не
сквозным шифрованием — содержимое им доступно. Хранится до доставки, срок жизни
выставлен 45 секунд (столько же, сколько звонит вызов), дальше отбрасывается.

**Решение Eugene: оставить как есть.** Позывные и названия групп не считаются
секретными, а мгновенный понятный экран звонка («ЭЛЕНА звонит в группе Family»)
важнее. Рассматривался и отклонён вариант слать только `callId` с дозапросом
подробностей у нашего сервера: у Apple остался бы бессмысленный идентификатор,
но при плохой связи на экране было бы безымянное «Входящий вызов».

**Это не новая категория раскрытия:** ровно те же поля уже уходят в Google через
FCM для Android-побудки.

**Про `responseToken` отдельно.** Это единственный настоящий секрет в полезной
нагрузке — но он одноразовый, живёт время звонка и позволяет ровно одно:
отметить вызов принятым или отклонённым. Разговор по нему не подслушать и в
систему не войти. Нужен затем, чтобы нативный экран отвечал НЕ дожидаясь запуска
WebView, иначе «Ответить» тормозило бы на секунды. Убирать его — значит портить
то, ради чего всё делается.

## Universal Links — серверная половина готова

Чтобы QR-приглашение открывало приложение, а не Safari (iOS-аналог Android App
Links из D6), нужны две половины. **Серверная сделана:**

`web/public/.well-known/apple-app-site-association` — файл проверки
принадлежности. Отдаётся уже настроенным блоком nginx, где стоит
`default_type application/json`: **у файла нет расширения**, и без этой строки
он ушёл бы с неверным типом, а Apple такой файл не принимает.

Область намеренно узкая — только `/join/*`:

    "components": [{ "/": "/join/*" }]

Заявлять весь домен нельзя: тогда и обычные страницы сайта начали бы
открываться в приложении.

**Осталась половина на MacBook:** entitlement Associated Domains со строкой
`applinks:ptt.privox.tech` (шаг 2 выше). Пока его нет, файл просто лежит без
дела и ничего не ломает.

Проверить после выкатки:

    curl -sI https://ptt.privox.tech/.well-known/apple-app-site-association

Должно быть `200` и `content-type: application/json`, **без перенаправлений** —
Apple их не прощает.

## Решающий опыт — поставить сразу после первого рабочего звонка

Ответить на CallKit-звонок и проверить: **живёт ли разговор после сворачивания
приложения** (человек убрал телефон в карман или приложил к уху).

- **Живёт** — задача закрыта, фаза 2 не нужна. Тогда система годится и как
  замена обычным звонкам внутри организации.
- **Обрывается** — для полноценного разговора понадобится нативный звук
  (PushToTalk Framework), 3–5 недель.

**Не начинать фазу 2, пока этот опыт не поставлен.** От него зависит объём
работы, отличающийся в разы.

## Проверка серверной части без iPhone

Отправка на выдуманный токен — быстрый способ убедиться, что ключ, подпись и
тема в порядке (например, после переезда на другую машину):

    cd server && node --require ts-node/register -e "
    const { sendApns } = require('./src/services/apns.ts');
    sendApns('a'.repeat(64), { probe: 1 }, { pushType: 'voip' }).then(r => console.log(r));
    "

Ожидаемый ответ — `BadDeviceToken`. Если `InvalidProviderToken` — неверны ключ,
Key ID или Team ID. Если `403` с другой причиной — смотреть тему и bundle id.
