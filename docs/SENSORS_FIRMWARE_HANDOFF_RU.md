### СИМПТОМ 1+4 — датчик САМ снимается с охраны после движения ⇒ ПРИЧИНА В ПРОШИВКЕ (НЕ сервер, НЕ проводка)
Сервер armed сам НЕ меняет — проверено: `process.ts` `armed` не пишет; `telemetry.ts` меняет только по `setArmed` из тела; `/arm` — только явная команда. Значит снятие инициирует **сама плата**, шлёт `setArmed:false` из-за неверной классификации причины пробуждения.
**Механизм — опасный fallback в классификации wake** ([main.cpp:243-248](../../privox-sensors/motion_sensor/src/main.cpp#L243)):
```cpp
if (digitalRead(PIN_BUTTON) == LOW)       btn = true;        // кнопка
else if (armed && digitalRead(PIN_PIR) == HIGH) motion = true; // движение
else                                      btn = true;        // ← ВСЁ ПРОЧЕЕ = кнопка → toggle охраны!
```
- Движение будит плату (PIR wake HIGH). До чтения пина проходит время: `Serial.begin`+`delay(200)`, баннер, `gpio_hold_dis`. AM312 держит HIGH ~2с, но если импульс уже спал в LOW к моменту `digitalRead(PIN_PIR)` → условие `armed && PIR==HIGH` НЕ выполнено.
- Кнопка при этом HIGH (не нажата) → проваливаемся в `else btn=true` → плата считает «нажали кнопку» → `setArmed=!armed` → **снимает с охраны**.
- **Флак:** успел прочитать PIR HIGH → движение (аларм); не успел → снятие. Доп.: комментарий обещает «держим кнопку ~1с», но в коде один `digitalRead` без удержания/подтверждения.
**ФИКС (прошивка):** убрать fallback «всё прочее = кнопка». Кнопкой считать только ПОДТВЕРЖДЁННОЕ (удержание/перечитка ~50мс–1с) нажатие LOW; неоднозначный armed-wake трактовать как **движение** (или heartbeat), но НИКОГДА не как toggle охраны. Подробная инструкция: `privox-sensors/motion_sensor/FIX_SELF_DISARM_RU.md`.
**Попутно:** pull-up на PIR (AM312 сам гонит выход) — лишний, можно снять.
**На сервере подстраховка:** логировать каждую смену `armed` с источником (button/dispatcher/heartbeat) и временем — сразу видно, что инициатор = плата.

### СИМПТОМ 6 (вопрос Eugene) — один аккаунт диспетчера на ДВУХ компьютерах: проблема?
Для **приёма** уведомлений — НЕ проблема: single-session-вытеснения в коде НЕТ (второй логин первый сокет не рвёт), оба сокета входят в `user:` и `org:` ([socket/index.ts:91-95](../server/src/socket/index.ts)), room-emit (`sensor-update`/`sensor-alert`/PTT) доходит до ОБОИХ. Получат уведомление обе вкладки.
НО есть риски от общего аккаунта:
- **Presence по одному socketId:** `setUserOnline(userId, socket.id)` — состояние онлайн привязано к последнему сокету. Disconnect одного может пометить юзера офлайн, хотя второй жив → мигание presence у других.
- **PTT/floor по userId:** активный спикер/захват эфира кейятся по userId — два клиента под одним аккаунтом могут конфликтовать (двойной mute/перехват).
- Маскирует баги сокета: на одном компе уведомление пришло, на другом нет — выглядит как «иногда не приходит». **Возможный вклад в симптом 2b** (диспетчер смотрел на «тихую» вкладку, активная была на другом компе).
**Рекомендация:** для штатной работы — один аккаунт = одна активная сессия диспетчера; если нужен дубль-экран, лучше отдельные учётки. Глобально single-session не вводим без надобности (это поломает легитимные сценарии), но при диагностике сокет-багов сначала исключить второй открытый клиент.

### СИМПТОМ 3 — телефон был офлайн, вышел в онлайн → ничего ⇒ ПРИЧИНА: TTL пуша + нет реплея
FCM `ttl` в [push.ts:244](../server/src/services/push.ts) = **1 час** (`60*60*1000`). Телефон офлайн всю ночь (>1ч) → отложенный пуш **протухает и отбрасывается** → при выходе в онлайн ничего. Socket-алерты эфемерны (реплея пропущенного нет). Если токен был помечен невалидным (`enabled:false`) — пуш вообще не шлётся.
**ФИКС (правильный):** инциденты УЖЕ persист в БД (таблица `Incident`) — при загрузке приложения/реконнекте сокета **подтягивать открытые/недавние инциденты** (notification center), не полагаться на буфер FCM. TTL для тревог осознанно держать коротким (старый аларм вреден), поэтому надёжность — через дозагрузку из БД, а не через TTL.

### СИМПТОМ 5 — страница диспетчера/админа не всегда быстро рефрешится (нужно вручную обновить) ⇒ ПРИЧИНА: нет реконсиляции после пропуска события

## Задачи/проверки на стороне B8

### 1. Булево правило → инцидент (проверить, был баг)
Ранее: правило `motion=true → WARNING` принимало телеметрию (200), метрика отображалась, но **инцидент/аларм НЕ открывался** (числовые пороги работали). По последним тестам алармы по движению уже идут — **проверить, что boolean-правила стабильно открывают инцидент** и это не регрессирует. Воспроизведение: `POST {"metrics":{"motion":true}}` на push-датчик с правилом `motion=true→WARNING`.

### 1b. ⚠️ Движение в armed: на панели красное, но УВЕДОМЛЕНИЕ не приходит
Симптом (наблюдалось вживую): датчик в armed, движение сработало → телеметрия дошла, в разделе Sensors статус **красный**, но **уведомление/аларм диспетчеру не сформировалось**. Поведение нестабильное: то красное гаснет само (авто-гашение? или прилетел ручной `motion:false`), то снова загорается при повторном движении — но уведомления всё равно нет.
**ВЕРОЯТНАЯ ПЕРВОПРИЧИНА (важно): изменился ПАТТЕРН потока, не формат.**
Формат тела не менялся — всегда `{"metrics":{"motion":true}}`. Но:
- раньше (always-on) плата слала **чистые пары** `motion:true` / `motion:false` → каждое движение = фронт `false→true`;
- теперь (deep sleep) плата будится только по подъёму, шлёт `motion:true` и засыпает; `motion:false` **больше не шлёт** (спит, когда движение кончилось) → на сервере `motion` **залипает в true**.

Если уведомление формируется **на фронте `false→true`**, то при залипшем `true` следующее `motion:true` — **не фронт** → уведомление не создаётся, хотя панель красная. Это объясняет «красное есть — аларма нет» и «иногда приходит» (когда `motion` успел сброситься авто-таймаутом/ручным `motion:false`, появляется новый фронт).

**Фикс — тот же, что в п.3b:** сервер должен трактовать `motion` как **импульс-событие** и авто-сбрасывать его по таймауту. Тогда каждое движение снова даёт фронт `false→true`, и уведомления восстанавливаются. Прошивку менять НЕ нужно (она и не может слать `motion:false` из сна). Доп. проверить: учитывается ли `armed` при доставке; дедуп инцидента не глотает ли нотификацию; работает ли доставка на boolean-метрику (п.1). Плата шлёт `{"motion":true}` → `200`, её часть исправна.

### 1c. Звук push-уведомления на телефоне не приходит
Симптом: при срабатывании уведомление приходит, но **без звука** на телефоне (беззвучно). Разобрать на стороне сервера/приложения: payload push (FCM) — задан ли `sound`/notification channel с звуком; маппинг severity (WARNING) → канал со звуком; не уходит ли как «тихое»/data-only сообщение. Скорее всего настройка канала уведомлений или поля push, не прошивка.

⚠️ **Уточнение (Eugene, 2026-06-12): это был ЗАВИСШИЙ КЛИЕНТ на одном телефоне, не сервер.** Push не приходил **на одном конкретном телефоне**, на остальных норм. ВАЖНО: **выключение/включение питания НЕ помогло — помог только выход из аккаунта и повторный вход (релогин).** Значит проблема не в железе телефона и не в Doze/батарее, а в **залипшем состоянии сессии/клиента** (протухший/невалидный FCM-токен, не переподписанный в БД; мёртвая сокет-сессия, которую не оживляет рестарт приложения; кэш PWA/service worker). Посмотреть на стороне приложения/сервера: жизненный цикл и ре-регистрация FCM-токена при старте, инвалидация старых токенов, почему рестарт ОС не пересоздаёт подписку, а релогин — да. Воспроизвести и понять корневую причину, т.к. это может повторяться у пользователей в поле.

### 1d. ⚠️ Датчик иногда САМ снимается с охраны (armed→disarmed без команды)
Симптом (Eugene, 2026-06-12): датчик периодически **самопроизвольно снимается с охраны** — никто кнопку не жал и диспетчер не снимал. Источник неясен: сервер или прошивка. Кандидаты на проверку:

**Сторона прошивки (motion_sensor, deep sleep):**
- `armed` лежит в `RTC_DATA_ATTR`. **Brownout/просадка питания / полный сброс RTC-памяти → `armed` теряется и инициализируется дефолтом (disarmed).** Самый вероятный подозреваемый на батарейном питании. Проверить: что в дефолте, логировать причину reset (`esp_reset_reason`), и при потере RTC — подтягивать armed С СЕРВЕРА (источник правды), а не вставать в disarmed.
- Определение причины пробуждения чтением пина: **ложный LOW на кнопочном пине GPIO5 (наводка/дребезг/плавающий вход во сне) читается как нажатие → toggle armed → снятие.** Проверить устойчивость подтяжки во сне и фильтрацию.
- Логика exit delay / `exitDelayPending` — не оставляет ли в каком-то пути disarmed.

**Сторона сервера B8:**
- Не шлёт ли что-то `setArmed:false` неявно; нет ли гонки на heartbeat (плата прислала старое состояние → перезатёрла серверное); не сбрасывает ли disarmed логика arm/disarm на уровне датчика при каком-то событии.

**Как ловить:** логировать КАЖДУЮ смену `armed` на сервере с источником (кнопка/диспетчер/heartbeat/reset) и временем — сразу видно, кто инициатор. На плате — лог `esp_reset_reason` и причины пробуждения. Связано с RTC-логикой в ARM_SLEEP.md §Стадия B.

### 2. Telegram-уведомления «поставлено / снято с охраны» (НОВОЕ)
При смене `armed` группы/датчика слать уведомление в Telegram (напр. в группу Family).
- Плата уже сообщает смену (`setArmed`), сервер — источник правды по `armed` → ему и слать.
- Прошивку не трогаем.
- Сделать через меню/настройку: вкл/выкл уведомлений, выбор чата/канала. Ложится в §14.4 (политика оповещений: severity → каналы) и §209 (каналы оповещения) плана.

### 3. Модель инцидента: дедуп, чтобы не «алертить каждые 5 минут»
Heartbeat несёт текущее `motion`. Инцидент должен открываться **на фронте** (motion false→true), висеть пока активно, закрываться на спаде — без нового аларма на каждый повторный `true`. См. §14.2 (Incident) плана.

### 3b. ⚠️ ПРИОРИТЕТ: авто-гашение `motion` по таймауту (для спящих PIR)
Батарейный PIR в deep sleep будится **только по подъёму** движения и шлёт `motion:true`, после чего засыпает. Когда движение кончилось — плата **спит и НЕ может прислать `motion:false`**. Поэтому на сервере `motion` зависает `true` до следующего heartbeat (в armed — до 60 мин). Наблюдалось вживую: аларм висит «4 минуты и больше» без движения.
**Решение на B8:** трактовать `motion` как **событие-импульс** и авто-сбрасывать его / закрывать инцидент через настраиваемый таймаут (напр. 30–60 c) после последнего `motion:true`, не дожидаясь явного `motion:false`. Опираться на `ts`/время прихода. Это стандарт для батарейных PIR (Zigbee/ESPHome). Альтернатива «ждать motion:false» не работает со спящим датчиком и жжёт батарею.

### 4. UX: push-датчик невидим в панели Sensors, пока не пушнул
На этапе ручного теста датчик не виден, пока не сделает первый POST, и «затихает» между редкими пушами. Предложение: показывать зарегистрированный push-датчик и без данных (placeholder «no data yet»), а не скрывать.
