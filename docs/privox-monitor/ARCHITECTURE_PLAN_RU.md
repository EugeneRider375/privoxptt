# Privox Monitor — архитектура и план реализации (вариант B)

> Статус: **план, не в работе.** Создано 2026-06-13.
> Дополняет [PRIVOX_MONITOR_RU.md](PRIVOX_MONITOR_RU.md) — там продукт/вертикали, тут *как строим*.
> Решение принято в обсуждении 2026-06-13: **отдельный сайт для потребителя, общий бэкенд под капотом.**

---

## 0. Главный принцип

**Для потребителя — два разных продукта. Под капотом — один движок датчиков.**

- Клиент Monitor не знает, что существует PTT. Свой сайт, свой логин, свой бренд.
- Датчиковый код (приём телеметрии, правила, инциденты, пуши) **не дублируется** — это тот же бэкенд, что уже на проде в PrivoxPTT.
- Никакого форка/копии. Дубль кода датчиков = двойная поддержка = запрещено.

```
                  ┌──────────────────────────────┐
                  │   ОБЩИЙ БЭКЕНД (как на проде)  │
                  │   POST /api/telemetry          │
                  │   правила / пороги             │
                  │   инциденты (entry delay,       │
                  │     авто-сброс, сирена)        │
                  │   FCM-пуши                     │
                  │   + tenant_id (НОВОЕ)          │
                  │   + Telegram-бот (НОВОЕ)        │
                  └───────────────┬──────────────┘
              ┌───────────────────┴───────────────────┐
       ptt.privox.tech                          monitor.privox.tech
       (фронт PTT — как есть)                   (НОВЫЙ фронт, отдельный)
       рации/группы/диспетчер                   дашборд датчиков, без PTT
```

## 1. Решения по открытым вопросам (раздел 9 ТЗ)

| Вопрос | Решение |
|---|---|
| Домен | **`monitor.privox.tech`** — отдельный поддомен, отдельный визуал. |
| Монорепо vs отдельный репо | **Отдельный фронт** (можно отдельная папка в корне IT Projects), **общий бэкенд**. К монорепо причёсываем позже, когда появится время. |
| Регистрация | На старте — **аккаунты заводим вручную** (OWNER на каждого клиента). Самостоятельная регистрация + биллинг — Ф3. |
| Биллинг | Позже (Ф3). |

## 2. Бэкенд: мультиарендность (`tenant_id`) — единственная серьёзная правка

Цель: клиент Monitor видит **только свои** датчики/инциденты. Сейчас данные не разделены по арендаторам.

**Что добавить:**
1. Сущность арендатора (`Tenant` / переиспользовать `Organization` из ТЗ §3).
2. Поле `tenant_id` (FK) на: `Sensor`, `Incident`/инциденты, пользователей-владельцев.
3. Привязка входящей телеметрии к арендатору — по device-ключу/токену датчика (датчик уже шлёт ключ в `/api/telemetry`).
4. Фильтрация всех запросов Monitor-фронта по `tenant_id` текущего пользователя (middleware/scope).
5. Роль **OWNER** — владелец аккаунта арендатора (видит свой tenant целиком).

**Чего НЕ трогаем:** PTT-часть (группы, presence, mediasoup, звонки) — она к Monitor отношения не имеет, остаётся как есть. PTT-пользователи и Monitor-арендаторы не пересекаются.

**Миграция:** существующие датчики B8 (уже на проде) → присвоить дефолтному tenant, чтобы прод не сломался.

---

## 3. Telegram-бот для алармов (фаза 1 оповещений)

- Клиент привязывает `chat_id` / канал к своему tenant.
- Бэкенд при срабатывании правила/отбое/офлайне датчика шлёт сообщение в Telegram этого tenant.
- Минимум трения для клиента (не надо ставить PWA, чтобы получать алармы).
- FCM-пуши (уже есть) остаются как второй канал.

---

## 4. Новый фронт `monitor`

- Отдельное приложение (своя папка), свой брендинг **Privox Monitor**, свой логин — **без единого упоминания PTT**.
- Дёргает существующий API бэкенда (тот же, что у PTT), но только датчиковые эндпоинты + scope по tenant.
- Можно переиспользовать API-клиент / типы из `web/` PrivoxPTT (общий пакет позже).

**Экраны MVP** (из ТЗ §4):
- Дашборд датчиков: статус OK/ALERT/STALE, последнее значение, батарея/связь, время, карта.
- Карточка датчика: история/графики, пороги, вкл/выкл сирены/уведомлений.
- Настройка датчика: выбор типа/пресета + ручная подстройка порогов.
- Лента инцидентов.

## 5. Деплой

- Coolify: новый сервис `monitor-frontend` на тот же бэкенд.
- DNS: `monitor.privox.tech` → сервис фронта.
- Бэкенд один (как сейчас, `ptt.privox.tech` для API) — Monitor-фронт ходит на него.
- ⚠️ Помнить про **автодеплой по пушу в main** ([[deploy_plan]]) — мелочи в main не пушить.

---

## 6. Порядок работ (для отдельного чата, где будем кодить)

1. **Бэкенд `tenant_id`** — модель Tenant/Organization, FK на Sensor/Incident/User, scope-middleware, миграция дефолтного tenant для B8. ← фундамент, без него Monitor не разделяет клиентов.
2. **Роль OWNER** + ручной завод аккаунтов клиентов.
3. **Telegram-бот** — привязка chat_id к tenant + рассылка алармов.
4. **Новый фронт `monitor`** — каркас, логин, дашборд, карточка датчика, инциденты, бренд.
5. **Деплой** — `monitor.privox.tech` в Coolify, DNS.
6. **Пресеты по вертикалям** (ферма, cold chain) — Ф2.

---

## 7. Почему малорискованно

Тяжёлое (приём телеметрии, правила, инциденты, охрана/entry delay, сирена, пуши) **уже на проде**.
Monitor = **новый фронт + tenant_id + Telegram-бот + роль OWNER + пресеты** поверх готового ядра. Бэкенд датчиков пишется один раз и обслуживает оба продукта.
