# B8 — Универсальные датчики: подробный план

Дата: 2026-06-10. Статус: ПЛАН (не реализовано). Развивает уже готовое
(см. `docs/SENSORS_RU.md`, B4 — управление датчиками в проде).

---

## 1. Цель и что получим в результате

Сейчас система понимает только **температуру и влажность** и только источники
формата Frigo/HomeClimate. B8 делает её **универсальной**:

- **Любой тип датчика:** температура, влажность, **уровень воды**, **протечка**,
  **движение**, **открытие двери**, CO₂, заряд батареи и т.д.
- **Новые датчики без написания кода** — устройство просто шлёт свои показания в
  стандартном формате, и оно появляется в системе.
- **Единый дашборд и единое управление** для всех датчиков, независимо от типа и
  источника, при этом **за каждым можно следить отдельно** (история, графики).
- **Тревоги/push/группы** работают так же, как сейчас.

Итог: PrivoxPTT становится реальной «единой системой датчиков с алармами» из
обещания сайта, а не только температурой.

---

## 2. Ключевая идея: МЕТРИКИ и их ТИПЫ

Вместо жёстких полей `temperature`/`humidity` вводим понятие **метрика** —
именованное показание. У каждой метрики есть **тип**:

| Тип | Примеры | Порог-правило |
|-----|---------|---------------|
| **number** (число) | температура °C, влажность %, **уровень воды см/%**, CO₂ ppm, заряд % | диапазон **min/max** (тревога если вне) |
| **boolean** (да/нет, событие) | **протечка**, **движение**, **дверь открыта** | **тревога когда true** (или false — настраивается) |

Показания датчика — это просто объект метрик:
```jsonc
{ "temperature": 5.1, "humidity": 60 }              // холодильник
{ "waterLevel": 82, "leak": true }                  // датчик воды
{ "motion": false, "doorOpen": true, "battery": 87 } // охранный
```
Тип метрики выводится из значения (число → number, true/false → boolean), плюс
можно переопределить ярлык/единицу в настройках.

## 3. Два пути подключения датчика

### Путь A — PUSH (стандартная телеметрия) — ГЛАВНЫЙ для новых датчиков
Устройство само шлёт показания на один эндпоинт:
```
POST https://ptt.privox.tech/api/telemetry
Header: X-Sensor-Key: <ключ датчика>
{ "metrics": { "waterLevel": 82, "leak": true }, "ts": 1718000000 }
```
- Сервер по ключу находит датчик, сохраняет метрики, проверяет пороги, шлёт тревоги.
- **Ноль кода под новый датчик** — plug-and-play. Любой ESP/шлюз, умеющий POST.
- Так подключаются: датчик воды, движения, двери, **LoRaWAN-шлюз** (шлюз
  пересылает аплинки LoRa-устройств этим POST'ом — одна интеграция, дальше любые
  LoRa-датчики).

### Путь B — PULL (адаптер) — для готовых облачных API
Для источников со своим API (Frigo, HomeClimate, будущие вендоры):
- SUPERADMIN указывает `sourceUrl` + выбирает **адаптер**.
- Поллер каждые 15с тянет URL, **адаптер** (маленький код) превращает ответ в метрики.
- Новый тип облачного источника = новый адаптер (короткий код, делает разработчик).

**Вывод:** новые «наши» датчики (вода, LoRa) идут через **push — без кода**.
Чужие облачные сайты — через адаптер.

---

## 4. Как будет выглядеть ДОБАВЛЕНИЕ датчика

В админ-панели «Sensors» кнопка **Add** → выбор типа подключения:

### Вариант «Push-устройство» (наш датчик)
1. Имя, тип (выбор иконки/категории), организация, группа (куда тревоги).
2. Система **генерирует уникальный ключ** `sensorKey` и показывает:
   - ключ (с кнопкой «копировать»),
   - URL эндпоинта `/api/telemetry`.
3. Эти ключ+URL прошиваешь в устройство (ESP/шлюз). Как только оно пришлёт первый
   POST — метрики появятся, и можно настроить пороги.

### Вариант «Pull-источник» (облачный API)
1. Имя, тип, группа.
2. Адаптер (FRIGO / HOMECLIMATE / …), sourceUrl, externalId.
3. Поллер сразу начинает тянуть.

Метрики у датчика **появляются сами** из присланных данных — не нужно заранее
описывать схему. Увидел метрику → настроил по ней порог.

## 5. Как будет выглядеть УПРАВЛЕНИЕ

Развиваем уже готовую страницу «Sensors» (B4):

- **Список датчиков:** имя · статус 🟢/🔴/⚪ · **его метрики** (динамически: где
  temp/hum, где waterLevel/leak, где motion/door) · группа · вкл/выкл.
- **Выпадающая панель настроек** (на датчик) — пороги **рендерятся по метрикам**:
  - метрика-**число** → поля **min/max** + единица (°C, %, см…),
  - метрика-**boolean** → переключатель «тревога когда ВКЛ / ВЫКЛ».
  - привязка к **группе** (распределение тревог/push), вкл/выкл, имя.
  - для **push-устройства** — показ `sensorKey` + URL (для настройки устройства).
- **Распределение по диспетчерам/группам/абонентам:** через `groupId` датчика —
  тревога/push летят в нужную группу (как сейчас). Тонкую видимость per-диспетчер
  (отдельный пункт) можно добавить позже.
- **Дашборд диспетчера** (панель SENSORS) — показывает **любые метрики**, не
  только temp/hum; красная тревога — как сейчас.
- **Индивидуальное наблюдение:** клик по датчику → его история/график по каждой
  метрике (на базе `SensorReading`).

## 6. Модель данных (изменения Prisma)

`Sensor` (добавить):
- `ingest` enum **PULL | PUSH** (как поступают данные).
- `sensorKey` String? @unique (для push-устройств; null для pull).
- `thresholds` Json — **обобщить** формат:
  ```jsonc
  { "temperature": { "type":"number", "min":2, "max":8 },
    "leak":        { "type":"boolean", "alertWhen": true } }
  ```
- `lastValue` Json — уже произвольный, хранит любые метрики.
- (опц.) `metricsSpec` Json? — ярлыки/единицы метрик (автозаполняется, редактируется).

`SensorReading` — обобщить: вместо колонок `temperature/humidity` хранить
`metrics` Json (+ при желании оставить temp/hum для совместимости/графиков).

Миграция — аддитивная, существующие датчики не ломает.

## 7. Бэкенд (что меняется)

1. **`POST /api/telemetry`** — новый роут (push-протокол): ключ → датчик → запись
   метрик → проверка порогов → emit (как `sensor-alert` сейчас) + push в группу.
2. **`evaluateThresholds`** — обобщить: идти по всем метрикам в `thresholds`,
   number → вне [min,max], boolean → `value === alertWhen`.
3. **Адаптеры** — отдавать обобщённый `metrics: Record<string, number|boolean>`
   (normalizeFrigo → {temperature}, normalizeHomeclimate → {temperature, humidity}).
4. **Поллер** — хранить/проверять метрики обобщённо (для PULL-датчиков).
5. **STALE-детект** — как сейчас (молчание > N мин).

## 8. Тревоги и распределение (как сейчас)
Без изменений по сути: при пробое порога → `sensor-alert` в `org:` и в группу
датчика + FCM-push участникам группы. Голос (TTS/авто-вызов) — отдельный пункт.

---

## 9. Совместимость с текущими датчиками
Frigo/HomeClimate продолжают работать: адаптеры дают те же метрики; пороги
temp/humidity → получают `type:"number"` (по умолчанию). Им проставляется
`ingest=PULL`, `sensorKey=null`. Ничего переделывать вручную не надо.

---

## 10. Как лягут вода / движение / дверь / LoRaWAN
- **Уровень воды** — метрика-**число** (`waterLevel`), порог max (затопление). Плюс
  отдельная boolean `leak` (факт протечки) если датчик её даёт.
- **Движение / дверь** — метрики-**boolean** (`motion`, `doorOpen`), тревога когда true.
- **LoRaWAN** — шлюз принимает аплинки и шлёт стандартный `POST /api/telemetry`
  по каждому устройству. Дальше любые LoRa-датчики — без кода в PrivoxPTT.

## 13. B10 — Двухуровневый мониторинг (платформа + эскалация)

**Идея (Eugene):** система датчиков = самостоятельная ПЛАТФОРМА. PrivoxPTT — лишь
один потребитель (экстренное реагирование). Поверх ядра приёма (B8) — несколько
выходов, маршрутизация по ВАЖНОСТИ события.

### Архитектура
```
Датчики (push/pull) → ЯДРО (приём+пороги+severity) →
   ├─ 📊 Независимый МОНИТОР (отдельный продукт, напр. sense.privox.tech) — владелец смотрит всё
   ├─ 📲 TELEGRAM владельцу — любые события (корова/вода/мороз)
   └─ 🚨 PrivoxPTT — ТОЛЬКО critical → диспетчер + группа реагирования (push/голос)
```

### Severity у порога
Каждое правило помечается важностью: **info / warning / critical**. Маршрут зависит
от severity (info/warning → владельцу; critical → ещё и в PrivoxPTT).

### Каналы оповещения (настройка на датчик/правило/предприятие)
- **Telegram** (чат владельца) — какие severity слать. Обобщить бота Frigo
  (chatId на предприятие/датчик).
- **Независимый монитор** — ОТДЕЛЬНЫЙ продукт-портал (sense.privox.tech): только
  датчики, история, графики, без PTT-консоли. На том же ядре/БД.
- **Эскалация в PrivoxPTT** (только critical):
  - **настраивается** — своя группа предприятия И/ИЛИ **внешняя служба спасения**
    (cross-org: датчик фермы → группа другого предприятия-спасателя).
  - Нужна модель «правило эскалации»: `{ severity, targetOrgId?, targetGroupId }`.

### Сценарий «ферма»
- Хозяин смотрит монитор дома; вода на исходе/корова/мороз → `warning` → Telegram ему.
- Наводнение → `critical` → Telegram ему + тревога в PrivoxPTT → диспетчер + группа
  реагирования (своя и/или внешняя служба спасения) с push/голосом.

### Два продукта на одной платформе
- **PrivoxSense** — мониторинг + Telegram для владельцев (sense.privox.tech).
- **PrivoxPTT** — экстренная связь/реагирование. Связаны эскалацией critical.

### Решения (согласовано 2026-06-10)
- Эскалация critical: **и своя группа, и внешняя служба — по настройке** (cross-org).
- Независимый монитор: **отдельный портал/продукт**, не режим внутри PTT.

### Этапность
B8 (ядро универсальных датчиков) → потом B10 (severity + Telegram + монитор-портал +
cross-org эскалация). B8 — фундамент, без него B10 не делать.

## 14. Уточнения модели — ЗАЛОЖИТЬ СРАЗУ (влияют на схему БД)

Эти 5 вещей дёшево заложить сейчас и дорого ретрофитить. Для системы безопасности
критичны (ложняки и «тихие отказы» убивают доверие).

### 14.1 Пороги = массив ПРАВИЛ с severity и дебаунсом (не один диапазон)
Вместо `thresholds: { temperature: {min,max} }` — массив правил:
```jsonc
"rules": [
  { "id":"r1", "metric":"waterLevel",  "op":"gt",      "value":80, "severity":"warning",  "sustainedSec":120 },
  { "id":"r2", "metric":"waterLevel",  "op":"gt",      "value":95, "severity":"critical", "sustainedSec":120 },
  { "id":"r3", "metric":"temperature", "op":"outside",  "min":2, "max":8, "severity":"critical" },
  { "id":"r4", "metric":"leak",        "op":"is",      "value":true, "severity":"critical" }
]
```
- `op`: gt / lt / outside(min,max) / is(boolean).
- **severity** на КАЖДОЕ правило → разные уровни (вода 80=warning, 95=critical).
- **`sustainedSec`** = дебаунс: условие должно держаться N секунд, иначе не срабатывает
  (волна плеснула → не наводнение).

### 14.2 Жизненный цикл тревоги — модель `Incident`
Тревога не «пикнул и забыл», а сущность с состоянием:
```
model Incident {
  id, sensorId, ruleId, metric, severity, message, peakValue
  status: OPEN | ACKNOWLEDGED | RESOLVED | MUTED
  openedAt, acknowledgedAt, acknowledgedBy, resolvedAt, lastNotifiedAt
}
```
- Открывается когда правило сработало (с учётом sustainedSec); **auto-resolve** когда
  значение вернулось в норму.
- **acknowledge** — диспетчер/владелец «принял».
- **повтор-нотификация** если всё ещё OPEN+critical через N мин.
- **mute/snooze** — заглушить на время (плановое обслуживание) без спама.
- Дашборд/монитор показывают список **активных инцидентов**, а не поток разовых пиков.

### 14.3 Здоровье устройства (батарея / связь / офлайн)
Молчащий датчик безопасности = опасность. Поля у `Sensor`:
- `reportIntervalSec` — ожидаемый интервал отчёта (null = событийный, как дверь).
- `batteryPct`, `rssi` (или как обычные метрики battery/rssi в payload).
- **STALE — per-sensor** (по reportIntervalSec), а НЕ глобальные 20 мин: LoRa спит и
  шлёт раз в час — норма; WiFi молчит сверх интервала — тревога «офлайн».
- Системные тревоги: **«датчик офлайн»**, **«низкий заряд»** (тоже severity).
- Событийные датчики (дверь/движение) — опц. периодический heartbeat-пинг, чтобы
  отличать «тихо, потому что нет события» от «тихо, потому что сдох».

### 14.4 Политика оповещений (severity → каналы + эскалация)
Обобщить вместо 3 захардкоженных выходов. Модель `NotificationPolicy`
(на предприятие, с переопределением на датчик):
```jsonc
[
  { "severity":"warning",  "channels":[{"type":"telegram","chatId":"..."},{"type":"monitor"}] },
  { "severity":"critical", "channels":[
      {"type":"telegram","chatId":"..."},
      {"type":"ptt_group","groupId":"..."},                  // своя группа
      {"type":"ptt_group","orgId":"rescue-org","groupId":"..."}, // внешняя служба (cross-org)
      {"type":"email","to":"..."},
      {"type":"webhook","url":"..."}
    ],
    "escalation":[ {"afterSec":300,"ifStatus":"OPEN","channels":[ /* поднять выше */ ]} ]
  }
]
```
- Каналы: **telegram / monitor / ptt_group (своя или внешняя) / email / webhook**.
- **Эскалация:** если инцидент всё ещё OPEN через afterSec → доп-каналы (выше по цепочке).

### 14.5 На потом (не ломает модель)
Ретеншн/даунсэмплинг истории (сырые 7 дней + почасовые на год); зоны/карта;
калибровка (offset/scale на метрику); тест-тревога (проверить цепочку); команды/
актуация (насос/клапан — downlink). Архитектуру под это не закрывать.
